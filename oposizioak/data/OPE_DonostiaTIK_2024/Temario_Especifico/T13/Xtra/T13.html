1. Datos y anclas de memoria

  • DEBIAN → APT → .DEB · RED HAT → DNF → .RPM (SUSE → Zypper → .rpm). Ubuntu está dentro de la familia Debian.
  • Linux = kernel · Distribución = kernel + herramientas + gestor + configuración.
  • systemd → PID 1 (no es el kernel) · systemctl → SERVICIOS · journalctl → JOURNAL.
  • start = ahora · enable = arranque automático.
  • SSH → 22; clave pública en el servidor, privada en el cliente.
  • root → TODO · sudo → ELEVACIÓN PUNTUAL.
  • LVM → FLEXIBILIDAD (capa entre almacenamiento físico y volúmenes lógicos; no es un sistema de archivos).
  • df → SISTEMA DE ARCHIVOS · du → DIRECTORIOS/ARCHIVOS · free → MEMORIA · ss → RED · ps → instantánea · top/htop → interactivo.
  • Instalación desatendida: Kickstart (Red Hat) · Autoinstall (Ubuntu Server) · preseed (Debian clásico).
  • Actualización automática: unattended-upgrades (Debian/Ubuntu) · dnf-automatic (Red Hat) — según configuración.
  • Sistemas de archivos: ext4 (extendido) · XFS (Red Hat, grandes volúmenes) · Btrfs (snapshots, subvolúmenes).
  • PV → VG → LV; ampliar el LV no amplía solo el sistema de archivos; XFS no se reduce.
  • Autoinstall → Ubuntu Server actual · preseed → instalador clásico de Debian · cloud-init → entrega la configuración, no la interpreta.
  • dnf makecache ≈ apt update · enable --now = habilitar + arrancar · active ≠ enabled · disable ≠ stop.
  • Clave de host → identidad del servidor (known_hosts).
  • available mejor que free · load ≠ % de CPU · df -i → inodos.

3. Posibles trampas de examen

  • «Linux es un sistema operativo completo» — impreciso en este contexto: Linux es el kernel; lo completo es la distribución.
  • «Ubuntu es una familia independiente de Debian» — falso: pertenece a la familia Debian (APT, .deb).
  • «apt update instala las actualizaciones» — falso: actualiza metadatos; instalar es apt upgrade.
  • «apt update equivale a dnf check-update» — falso: refrescar metadatos ≠ comprobar actualizaciones disponibles.
  • «systemd es el núcleo de Linux» — falso: es el primer proceso de espacio de usuario (PID 1) que arranca el kernel.
  • «systemctl enable arranca el servicio inmediatamente» — falso: configura el arranque automático; iniciar ahora es start.
  • «journalctl muestra todos los logs de cualquier aplicación» — falso: muchas aplicaciones escriben en /var/log.
  • «df y du muestran lo mismo» — falso: sistema de archivos vs. directorios/archivos.
  • «ps y top son intercambiables» — impreciso: instantánea vs. vista interactiva actualizada.
  • «root y sudo son lo mismo» — falso: superusuario vs. mecanismo de elevación puntual.
  • «La clave privada SSH se copia al servidor» — falso: la que se autoriza en el servidor es la pública.
  • «LVM es un sistema de archivos» — falso: es una capa de gestión de volúmenes.
  • «Un servidor Linux nunca puede tener interfaz gráfica» — falso: es una práctica habitual instalarlo sin GUI, no una imposibilidad.
  • «La actualización automática instala siempre todos los parches críticos» — matiz: depende de la configuración de la herramienta.
  • «LTS significa soporte indefinido» — falso: soporte prolongado con fecha de fin.
  • «CentOS Stream es lo mismo que el antiguo CentOS Linux» — falso.
  • «Ubuntu Server actual se automatiza con preseed» — falso: usa Autoinstall (Subiquity).
  • «cloud-init interpreta las directivas Autoinstall» — falso: las entrega; las procesa el instalador.
  • «Ampliar el LV amplía automáticamente el sistema de archivos» — falso: son dos pasos, salvo con opciones como lvextend -r.
  • «XFS se puede reducir» — falso.
  • «dpkg resuelve las dependencias como APT» — falso.
  • «systemd es el PID 1 en cualquier sistema Linux» — falso: lo es cuando actúa como sistema de inicio.
  • «systemctl disable detiene el servicio» — falso: solo quita el arranque automático.
  • «reload equivale siempre a restart» — falso.
  • «daemon-reload reinicia todos los servicios» — falso: systemd relee los ficheros de unidad.
  • «active y enabled significan lo mismo» — falso.
  • «El journal siempre se conserva tras reiniciar» — falso: depende de la configuración.
  • «SSH tiene que usar el puerto 22» — falso: es el puerto por defecto.
  • «Si la conexión SSH está cifrada, el servidor es el correcto» — falso: hay que verificar la clave de host.
  • «sudo ejecuta siempre como root» — falso: puede ejecutar como otro usuario.
  • «El live patching elimina todos los reinicios» — falso.
  • «Poca memoria free significa falta de RAM» — falso: hay que mirar available.
  • «Load average 4 es un 4 % de CPU» — falso: no es un porcentaje.
  • «df y du siempre suman lo mismo» — falso: por ejemplo, archivos borrados aún abiertos.
  • «Si df -h muestra espacio libre, siempre se pueden crear archivos» — falso: pueden faltar inodos.
  • «Un servicio active garantiza que la aplicación responde» — falso.

5. Posibles preguntas cortas (con esquema de respuesta)

1. Explique qué es una distribución Linux

  • Linux = kernel; distribución = kernel + herramientas + gestor de paquetes + configuración.
  • Las tres familias con su gestor y formato; Ubuntu dentro de Debian.
  • Cierre: LTS y su relevancia en servidores.

2. Diferencie APT y DNF

  • APT (Debian/Ubuntu, .deb) y DNF (Red Hat y derivados, .rpm); ambos resuelven dependencias desde repositorios.
  • Acciones equivalentes (instalar, actualizar) y las dos precisiones: update ≠ upgrade; apt update ≠ dnf check-update.
  • Cierre: dpkg y rpm como herramientas de bajo nivel.

3. Explique systemd, systemctl y journalctl

  • systemd: sistema de inicio y gestión de servicios; PID 1; no es el kernel.
  • Unidades (.service, .socket, .mount, .timer).
  • systemctl: start/stop/restart/status y enable/disable (start ≠ enable).
  • journalctl: consulta del journal; -u servicio; matiz sobre /var/log.

4. Explique el acceso remoto mediante SSH

  • Protocolo seguro de administración remota; cifrado; puerto 22/TCP.
  • Autenticación por contraseña o por claves (preferible).
  • Reparto de claves: pública en el servidor, privada en el cliente y protegida.

5. Diferencie root y sudo

  • root: superusuario con privilegios totales.
  • sudo: ejecución puntual de comandos con privilegios elevados desde una cuenta normal.
  • Cierre: buena práctica (usuario normal + sudo) y su ventaja en trazabilidad.

6. Explique LVM

  • Definición: capa de abstracción entre almacenamiento físico y volúmenes lógicos.
  • Ventajas: flexibilidad, agrupación de dispositivos, ampliación en determinados escenarios.
  • Matices: no todas las operaciones son posibles sin condiciones; LVM no es un sistema de archivos.

7. Explique las principales herramientas de monitorización

  • Procesos y recursos: top/htop, ps, free, uptime.
  • Almacenamiento: df y du. Red: ss.
  • Registros: journalctl y /var/log; mención de la monitorización centralizada como ampliación.

8. Diferencie df y du

  • df: espacio ocupado y libre por sistema de archivos.
  • du: espacio ocupado por directorios y archivos concretos.
  • Cierre: el procedimiento habitual — df para localizar el FS lleno, du para encontrar qué lo llena.

9. Diferencie Kickstart, preseed y Autoinstall

  • Kickstart: instalación desatendida de la familia Red Hat.
  • preseed: respuestas del instalador clásico de Debian.
  • Autoinstall: Ubuntu Server 20.04 y posteriores, en YAML, procesado por Subiquity; cloud-init puede entregarlo, no interpretarlo.

10. Explique PV, VG y LV

  • PV: disco o partición preparados para LVM. VG: suma de PV. LV: volumen que se asigna del VG.
  • Sobre el LV se crea el sistema de archivos y se monta.
  • Ampliar exige espacio libre en el VG y crecer también el sistema de archivos; XFS no se reduce.

11. Diferencie start, enable, active y enabled

  • start arranca ahora; enable programa el arranque con el sistema; enable --now hace las dos cosas.
  • active: está en marcha; enabled: arrancará al iniciar. Son independientes.
  • Ejemplo CAU: un servicio que falta tras reiniciar estaba active pero no enabled.

12. Interprete memoria, carga e inodos

  • free: mirar available, no solo free; la caché se libera.
  • Load average: procesos en CPU o esperando disco; según el número de núcleos; no es un porcentaje.
  • Inodos: con df -i; pueden agotarse con espacio libre.

6. Supuestos prácticos

Supuesto 1 — Un servicio no arranca

Escenario: tras un reinicio programado, un servicio de una aplicación municipal alojada en un servidor Linux no está disponible.

  • a) ¿Primer comando? systemctl status servicio: estado actual, últimos mensajes y si está configurado como enabled.
  • b) ¿Y si el estado no basta? journalctl -u servicio para ver los eventos con detalle.
  • c) ¿Qué más revisar? Configuración y dependencias del servicio; recursos y permisos (espacio en disco, memoria, puertos ocupados). Tras corregir, comprobar que la aplicación responde, no solo que el estado sea *active*.
  • d) Si arrancó a mano pero vuelve a faltar tras reiniciar, ¿qué ocurre? Lo más probable es que se hiciera start sin enable: no está configurado para arrancar con el sistema (se corrige con enable, o enable --now). No es la única causa posible: también una dependencia o un orden de arranque que falla.

Supuesto 2 — Sistema de archivos lleno

Escenario: un servidor empieza a fallar y se sospecha falta de espacio.

  • a) ¿Cómo confirmarlo? Con df: identifica qué sistema de archivos está al límite.
  • b) ¿Cómo localizar la causa? Con du dentro de ese sistema de archivos: qué directorios o archivos ocupan el espacio.
  • c) Sospechosos habituales. Registros acumulados (por ejemplo, bajo /var/log), copias temporales o volcados; la política de rotación y limpieza es parte del mantenimiento.
  • d) ¿Y si se borra un log enorme y df no baja? Un proceso mantiene abierto el archivo borrado: el espacio no se libera hasta que lo cierra (por ejemplo, al reiniciar el servicio de forma autorizada).
  • e) ¿Y si hay espacio pero no se pueden crear archivos? Se han agotado los inodos: df -i.

Supuesto 3 — Administrar el servidor desde el CAU

Escenario: hay que revisar la configuración de un servidor situado en el CPD sin desplazarse.

  • a) ¿Qué herramienta? SSH, protocolo seguro de administración remota (puerto 22/TCP por defecto).
  • b) ¿Qué autenticación conviene? Mediante claves: la pública autorizada en el servidor y la privada protegida en el equipo cliente.
  • c) ¿Con qué cuenta trabajar? Con un usuario normal, elevando con sudo las acciones que lo requieran.
  • d) ¿Qué se comprueba la primera vez que se conecta? La clave de host del servidor: la huella debe coincidir con la publicada por un canal oficial antes de aceptarla.

Supuesto 4 — Instalar y actualizar software

Escenario: hay que instalar un paquete nuevo y dejar el servidor actualizado en un servidor Ubuntu y en otro Rocky Linux.

  • a) ¿Qué gestor en cada uno? APT (.deb) en Ubuntu — familia Debian; DNF (.rpm) en Rocky — familia Red Hat.
  • b) ¿Qué pasos en APT? Actualizar metadatos (apt update), consultar lo actualizable (apt list --upgradable), actualizar (apt upgrade) e instalar (apt install). En Rocky: dnf makecache, dnf check-update, dnf upgrade y dnf install.
  • c) ¿De dónde sale el software y qué resuelve el gestor? De los repositorios configurados; el gestor resuelve automáticamente las dependencias.

Supuesto 5 — Ampliar el almacenamiento con flexibilidad

Escenario: un volumen de datos se queda corto y se prevé que siga creciendo.

  • a) ¿Qué tecnología conviene haber previsto? LVM: capa entre el almacenamiento físico y los volúmenes lógicos, que permite agrupar dispositivos y ampliar volúmenes en determinados escenarios. Si el VG no tiene espacio libre, se añade un disco como nuevo PV, se amplía el VG, después el LV y por último el sistema de archivos.
  • b) ¿Qué ventaja frente al particionado clásico? Flexibilidad: no queda todo fijado por el tamaño de partición inicial.
  • c) ¿Es una operación siempre trivial? No: las posibilidades de redimensionado dependen del sistema de archivos y del escenario; conviene planificar y respaldar.

Supuesto 6 — «El servidor va lento»

Escenario: los usuarios de una aplicación notan lentitud; hay que identificar qué está consumiendo el servidor.

  • a) ¿Qué herramientas usar? top/htop para ver en vivo qué procesos consumen CPU y memoria; ps para una instantánea concreta; free para el estado de memoria y swap; uptime para el load average.
  • b) ¿Cómo leer las cifras? En free, la columna available; el load average, según el número de núcleos. Una carga alta con CPU baja apunta a espera de disco.
  • c) ¿Y si se sospecha de la red? ss para conexiones y puertos en escucha.
  • d) ¿Dónde buscar rastro de errores? En journalctl y en los registros de /var/log.

Supuesto 7 — Mantener el servidor al día

Escenario: se plantea cómo gestionar las actualizaciones de varios servidores Linux.

  • a) ¿Opciones? Actualización manual planificada en ventana de mantenimiento, o automática con unattended-upgrades (Debian/Ubuntu) o dnf-automatic (Red Hat).
  • b) ¿Puede darse por hecho que lo instalarán todo? No: depende de la configuración de la herramienta.
  • c) ¿Qué más hay que vigilar? El ciclo de vida de la distribución: una versión sin soporte deja de recibir parches y obliga a planificar la migración. Y si se actualiza el kernel, prever el reinicio (o live patching, si está contratado).

Supuesto 8 — Activo, pero la web no responde

Escenario: systemctl status muestra el servicio web como *active (running)*, pero la aplicación no carga.

  • a) ¿Está resuelto? No: *active* solo dice que el proceso está en marcha.
  • b) ¿Qué comprobar? Con ss -tuln, que escucha en el puerto esperado; en el journal y en los registros de la aplicación, los errores; y la respuesta real desde un cliente.
  • c) ¿Qué no hacer? Reiniciar en bucle sin leer los registros.

Supuesto 9 — Aviso de clave de host cambiada

Escenario: al conectar por SSH a un servidor, el cliente avisa de que la identificación del equipo remoto ha cambiado.

  • a) ¿Qué significa? Que la clave de host no coincide con la guardada en known_hosts: o el servidor se reinstaló, o alguien se hace pasar por él.
  • b) ¿Qué hacer? No continuar; confirmar con el responsable del servidor, por un canal oficial, si hubo reinstalación y cuál es la huella nueva.
  • c) ¿Y después? Solo si se confirma, sustituir la entrada antigua de ese servidor. No borrar todo known_hosts para quitar el aviso.

Supuesto 10 — Reducir un volumen XFS

Escenario: se pide quitar espacio a un volumen con XFS para dárselo a otro.

  • a) ¿Es posible? No reduciendo XFS: ese sistema de archivos solo crece.
  • b) ¿Alternativa? Copia de seguridad, crear un volumen más pequeño, restaurar los datos en él y retirar el original, con procedimiento autorizado.
  • c) ¿Y con ext4? Se puede reducir, pero desmontado y con copia previa.

9. Resumen final: si mañana fuera el examen

  • Linux = kernel · distribución = kernel + herramientas + gestor + configuración. Familias: Debian (APT/.deb — incluye Ubuntu) · Red Hat (DNF/.rpm) · SUSE (Zypper/.rpm). LTS = soporte prolongado.
  • Instalación: ISO manual o desatendida (Kickstart en Red Hat; Autoinstall en Ubuntu Server actual; preseed en el instalador clásico de Debian; cloud-init solo entrega la configuración). Servidor habitualmente sin GUI (menos recursos y superficie de ataque), en la línea de Windows Server Core — no es una imposibilidad.
  • LVM → flexibilidad: PV → VG → LV; permite agrupar y ampliar (volumen y luego sistema de archivos); no es un sistema de archivos; XFS no se reduce. FS habituales: ext4, XFS, Btrfs.
  • Paquetes: repositorio, paquete, dependencia y gestor. apt update (metadatos) ≠ apt upgrade (instala); apt update ≠ dnf check-update (no son equivalentes exactos).
  • systemd: sistema de inicio y gestión de servicios, PID 1, no es el kernel. Unidades .service/.socket/.mount/.timer. systemctl: start (ahora) ≠ enable (arranque automático); enable --now hace las dos cosas; active ≠ enabled; disable no para. journalctl consulta el journal (-u servicio); no recoge todos los logs de todas las aplicaciones (/var/log).
  • SSH: administración remota cifrada, puerto 22/TCP, mejor claves — pública en el servidor, privada en el cliente; la clave de host identifica al servidor. root (todo) vs. sudo (elevación puntual); buena práctica: usuario normal + sudo.
  • Actualizaciones: manual o automática (unattended-upgrades / dnf-automatic, según configuración); vigilar el ciclo de vida y planificar migraciones; live patching como ampliación.
  • Monitorización: top/htop (procesos en vivo) · ps (instantánea) · free (memoria) · df (sistemas de archivos) · du (directorios) · uptime (load) · ss (red) · journalctl y /var/log (registros). available mejor que free; load ≠ % de CPU. Procedimientos: servicio caído → status + journalctl; disco lleno → df + du (y df -i).
