1. Linux y distribuciones

📌 Imprescindible para el examen
Linux → el kernel (núcleo del sistema operativo).
Distribución → kernel + herramientas de sistema + gestor de paquetes + configuraciones y otros componentes. Lo que se instala en un servidor es siempre una distribución, no «Linux» a secas.
Familia Distribuciones Gestor Formato
Debian Debian, Ubuntu Server APT .deb
Red Hat RHEL, Rocky Linux, AlmaLinux DNF .rpm
SUSE SLES, openSUSE Zypper .rpm

Ubuntu pertenece a la familia Debian (deriva de ella y comparte APT y el formato .deb): no es una familia independiente. Eso no hace intercambiables sus repositorios ni sus versiones: cada distribución mantiene los suyos. Sus versiones LTS (Long Term Support) tienen un ciclo de soporte prolongado, lo que las hace habituales en servidores; los años y fechas concretas son dato de actualidad, no materia nuclear.

  • LTS no es soporte indefinido: es un plazo prolongado pero fijo, que varía según producto y modalidad (estándar o ampliado de pago). Al acabar llega el fin de vida (EOL).
  • Formato ≠ gestor: .deb y .rpm son formatos de paquete; APT, DNF y Zypper son las herramientas que los gestionan.
  • Libre ≠ sin soporte comercial: Debian, Rocky o AlmaLinux son comunitarias; RHEL y SLES se distribuyen con suscripción de soporte, y Ubuntu ofrece soporte ampliado de pago (Ubuntu Pro).
  • En el lenguaje corriente se dice «el sistema operativo Linux» para referirse al sistema completo. Para el examen, la distinción es kernel ≠ distribución.
🔍 Para ampliar — CentOS, Rocky y Alma
CentOS Linux tradicional llegó a su fin de vida; CentOS Stream cumple otra función dentro del ecosistema Red Hat: es la rama de desarrollo por delante de las versiones menores de RHEL, no un clon de una versión ya publicada. Rocky Linux y AlmaLinux se orientan a la compatibilidad con RHEL, cada una con sus propias políticas; no son idénticas en todo. Los datos de ciclo de vida figuran, fechados, en la actualidad del tema (apartado 10 de Xtra).

2. Instalación de un servidor Linux

Métodos

  • Instalación manual: desde una imagen ISO, respondiendo de forma interactiva al instalador: idioma, almacenamiento y particionado, red, usuario inicial, selección de servicios, reinicio y comprobación.
  • Instalación automatizada/desatendida: las respuestas se aportan en un fichero de configuración, imprescindible para desplegar muchos servidores de forma idéntica y reproducible.
Mecanismo Dónde Qué hace
Kickstart Familia Red Hat Fichero de respuestas del instalador
preseed Instalador clásico de Debian (debian-installer) Respuestas del instalador clásico
Autoinstall Ubuntu Server 20.04 y posteriores (instalador Subiquity) Configuración declarativa en YAML
cloud-init Imágenes de nube y primer arranque Inicializa el sistema; también puede entregar la configuración Autoinstall
⚠️ No confundir — Autoinstall, preseed y cloud-init
El instalador actual de Ubuntu Server usa Autoinstall, no preseed: preseed es del instalador clásico de Debian.
cloud-init puede transportar la configuración Autoinstall, pero no la interpreta: la procesa el instalador (Subiquity).

Servidor sin entorno gráfico

Un servidor Linux suele instalarse sin entorno gráfico. Ventajas: menor consumo de recursos, menor superficie de ataque, menos componentes que mantener y actualizar, y administración por consola o SSH. Es una práctica habitual, no una imposibilidad técnica: un servidor Linux sí puede tener GUI si el caso lo justifica. Sin GUI no es sin interfaz: queda la shell en consola o por SSH. Y una instalación mínima reduce componentes, pero no garantiza por sí sola la seguridad.

🧠 Para memorizar — paralelismo
La filosofía coincide con la de Windows Server Core (Tema 12): menos componentes, menos superficie de ataque, administración por línea de comandos o remota.

Particiones, puntos de montaje y swap

  • Partición: trozo de un disco. Sistema de archivos: la organización de los datos dentro de una partición o volumen. Punto de montaje: el directorio donde se hace visible (/, /boot, /home, /var, /tmp).
  • Separar /var o /home es habitual en servidores para que un directorio que crece no llene la raíz, pero no es obligatorio en todas las distribuciones.
  • swap: espacio de intercambio, en partición o en archivo. Su funcionamiento es materia del Tema 9.
  • Antes de instalar se planifica: capacidad, sistema de archivos, red, actualizaciones, acceso administrativo y copia de seguridad.

LVM (Logical Volume Manager)

  • Qué es: una capa de abstracción entre el almacenamiento físico y los volúmenes lógicos.
  • Ventajas: flexibilidad, agrupación de dispositivos y volúmenes, ampliación de volúmenes en determinados escenarios y una administración más flexible que el particionado clásico de tamaño fijo.
  • Tres capas: PV (physical volume, el disco o la partición preparados para LVM) → VG (volume group, la bolsa de capacidad que suman uno o varios PV) → LV (logical volume, el volumen que se reparte de esa bolsa). Sobre el LV se crea el sistema de archivos y se monta.
  • Ampliar el LV no amplía por sí solo el sistema de archivos: son dos pasos (crecer el volumen y crecer el sistema de archivos), aunque hay herramientas que los coordinan, como lvextend -r. Y solo se puede crecer si queda espacio libre en el VG.
  • Reducir es otra cosa: XFS no se puede reducir; ext4 sí, pero desmontado y con copia previa.
  • Snapshot LVM ≠ copia de seguridad: depende del mismo almacenamiento (Tema 23). Y LVM ≠ RAID: LVM organiza; la redundancia es cosa del RAID.
🧠 Para memorizar
LVM → FLEXIBILIDAD. Y ojo: LVM no es un sistema de archivos, es la capa sobre la que se crean los volúmenes que luego se formatean.
DISCO → PV → VG → LV → SISTEMA DE ARCHIVOS → MONTAJE.

Sistemas de archivos habituales

Sistema Dónde se ve Crecer Reducir Snapshots propios
ext4 Muy extendido; por defecto en Debian y Ubuntu Sí, también montado Sí, desmontado No
XFS Por defecto en RHEL y derivados Sí, montado No No
Btrfs openSUSE y SLES, entre otros Sí Sí Sí, con subvolúmenes y sumas de comprobación
  • Ninguno es «el mejor» para todo: depende de la carga y de la distribución.
  • El journaling ayuda a recuperar la coherencia tras un corte; no es una copia de seguridad.
  • Un volumen puede existir sin estar montado: si no está montado, sus datos no se ven en ningún directorio.

3. Gestión de paquetes y del software

  • Repositorio: origen configurado de paquetes y de sus metadatos: un servidor oficial, un espejo o un repositorio interno de la organización.
  • Paquete: unidad de software distribuible (.deb o .rpm).
  • Dependencia: otro paquete necesario para que el software funcione.
  • Gestor de paquetes: instala, actualiza y elimina software resolviendo las dependencias desde los repositorios configurados (aunque un conflicto puede impedir la operación) y verificando las firmas de los paquetes. A bajo nivel existen dpkg (.deb) y rpm (.rpm), que instalan un paquete suelto sin resolver dependencias por sí mismos.
Acción APT (Debian/Ubuntu) DNF (Red Hat/Rocky/Alma)
Actualizar metadatos de repositorios apt update dnf makecache
Consultar actualizaciones disponibles apt list --upgradable dnf check-update
Actualizar los paquetes instalados apt upgrade dnf upgrade
Instalar un paquete apt install paquete dnf install paquete
Eliminar un paquete apt remove paquete dnf remove paquete
Buscar un paquete apt search término dnf search término

En SUSE, las mismas acciones se hacen con Zypper (zypper refresh, zypper update, zypper install).

⚠️ No confundir — dos precisiones
1) apt update ≠ apt upgrade: el primero actualiza los metadatos/caché de los repositorios (no instala nada); el segundo instala las versiones más recientes de los paquetes ya presentes.
2) apt update ≠ dnf check-update: no son equivalentes exactos. apt update refresca los metadatos; dnf check-update comprueba qué actualizaciones están disponibles. Lo más parecido a apt update es dnf makecache.
3) apt upgrade ≠ cambiar de versión de la distribución: actualiza paquetes dentro de la misma versión. Pasar de una versión a otra es una migración con su propio procedimiento. apt full-upgrade puede además añadir o retirar paquetes por cambios de dependencias, así que no se usa a ciegas.
  • Solo se instala desde repositorios autorizados: un paquete de origen dudoso es un riesgo.
  • Paquete instalado ≠ servicio funcionando: tras instalar, el servicio puede no estar iniciado, estar mal configurado o tener el puerto ocupado.

4. systemd y gestión de servicios

📌 Imprescindible para el examen
systemd → sistema de inicio y marco de gestión de servicios adoptado por la mayoría de distribuciones actuales (no por todas: existen otros sistemas de inicio).
PID 1 → es el primer proceso de espacio de usuario iniciado por el kernel. Cuando systemd es el sistema de inicio, systemd es el PID 1.
systemd ≠ kernel: el kernel arranca a systemd, no al revés.

Unidades (units)

  • .service: un servicio o demonio — la unidad más habitual.
  • .socket: activación por socket.
  • .mount: puntos de montaje.
  • .timer: los timers de systemd proporcionan un mecanismo integrado de programación de tareas y pueden utilizarse en lugar de cron en muchos escenarios (no son, sin más, «el reemplazo de cron»).
  • .target: agrupa unidades y marca estados del arranque (por ejemplo, multi-user.target, el modo servidor sin gráficos). Se parecen a los antiguos runlevels, pero no son idénticos.
  • Las unidades se relacionan por dependencias y orden de arranque: si falla una de la que depende un servicio, el servicio tampoco arranca.

systemctl

Comando Qué hace
systemctl start servicio Inicia el servicio ahora
systemctl stop servicio Lo detiene ahora
systemctl restart servicio Lo reinicia (lo para y lo vuelve a arrancar)
systemctl reload servicio Le pide releer su configuración sin pararlo, si el servicio lo admite
systemctl status servicio Consulta su estado y los últimos mensajes
systemctl enable servicio Configura su inicio automático con el sistema
systemctl enable --now servicio Lo habilita y lo arranca a la vez
systemctl disable servicio Quita el inicio automático; no lo detiene si está en marcha
systemctl mask servicio Bloquea la unidad: no se puede arrancar ni a mano ni por dependencia
systemctl daemon-reload Hace que systemd relea los ficheros de unidad tras editarlos; no reinicia los servicios
⚠️ No confundir — start ≠ enable
start arranca el servicio en ese momento. enable configura que arranque automáticamente con el sistema, pero no significa necesariamente que se inicie ahora. Y al revés: un servicio iniciado con start no quedará activo tras un reinicio si no está enabled. Para las dos cosas a la vez: enable --now.
⚠️ No confundir — los estados
active (systemctl is-active) → está en marcha ahora. enabled (systemctl is-enabled) → arrancará con el sistema. Son independientes: un servicio puede estar activo y no habilitado, o al revés.
static → la unidad no se habilita por sí misma; la activa otra. No es una avería.
failed → la unidad falló; la causa hay que buscarla en el estado y el journal.
disable ≠ stop · disable ≠ mask · reload ≠ restart · daemon-reload ≠ reiniciar servicios.

journalctl

  • journalctl consulta el journal gestionado por systemd.
  • journalctl -u servicio muestra los eventos de un servicio concreto — herramienta de diagnóstico de primer orden.
  • journalctl -b → desde el último arranque · journalctl -f → sigue los mensajes nuevos en directo · journalctl -p err → solo los de prioridad error o más grave.
  • Que el journal se conserve tras reiniciar depende de la configuración: puede ser persistente (en disco) o volátil (solo en memoria).
  • Matiz: el journal no contiene automáticamente todos los logs generados por cualquier aplicación Linux; muchas aplicaciones escriben sus propios ficheros, tradicionalmente bajo /var/log.
  • logrotate rota, comprime y elimina esos ficheros según una política. Los registros no se borran a mano «para ganar espacio» sin saber si hacen falta: pueden ser evidencias de un incidente.

5. Acceso remoto (SSH) y privilegios (root/sudo)

SSH

  • SSH (Secure Shell): protocolo seguro de administración remota, que cifra la comunicación entre cliente y servidor.
  • Puerto por defecto: 22/TCP. Se puede cambiar, pero cambiarlo no sustituye a una autenticación robusta. La implementación habitual es OpenSSH.
  • Métodos de autenticación: por contraseña o mediante claves criptográficas — preferible la autenticación por claves en entornos de producción.
📌 Imprescindible para el examen — las claves SSH
Clave pública → se instala/autoriza en el servidor.
Clave privada → permanece en el cliente y debe protegerse (nunca se copia al servidor), normalmente con una frase de paso (passphrase), que no es la clave sino lo que la protege.
Invertir esto es una trampa clásica.
⚠️ No confundir — clave del usuario y clave de host
El servidor tiene su propio par de claves, la clave de host, que demuestra su identidad al cliente. El cliente guarda las claves de host conocidas en known_hosts.
El cifrado no garantiza que se hable con el servidor correcto: si se acepta sin comprobar una clave de host desconocida, se abre la puerta a un ataque de intermediario.
Si aparece el aviso de clave de host cambiada, se verifica por un canal oficial (por ejemplo, porque el servidor se reinstaló) antes de aceptarla. Borrar known_hosts para que desaparezca el aviso no es la solución.

root y sudo

  • root: el superusuario, con privilegios totales sobre el sistema.
  • sudo: permite ejecutar comandos concretos con privilegios elevados desde una cuenta normal, de forma puntual y registrable. Lo que cada cuenta puede hacer lo fija la política sudoers; normalmente eleva a root, pero también puede ejecutar como otro usuario (sudo -u).
  • su: cambia de usuario en la sesión (por defecto, a root) pidiendo la contraseña de esa cuenta; sudo ejecuta un comando con la identidad autorizada y pide la contraseña propia.
  • root tiene los máximos privilegios convencionales, aunque mecanismos como SELinux, AppArmor o los contenedores pueden limitarlo.
  • Buena práctica: trabajar con un usuario normal + sudo, en lugar de iniciar sesión directamente como root, aplicando mínimo privilegio: se concede lo justo (por ejemplo, reiniciar un servicio concreto), no un sudo total. La gestión de usuarios y grupos es materia del Tema 14.

6. Actualizaciones y ciclo de vida

  • Actualización manual: con el gestor de paquetes (apartado 3), planificada en una ventana de mantenimiento.
  • Actualización automática: unattended-upgrades en Debian/Ubuntu y dnf-automatic en la familia Red Hat. Lo que se instala automáticamente depende de la configuración (orígenes permitidos, tipos de actualización, ventanas): no debe darse por hecho que siempre instalan todos los parches críticos, ni que reinicien el servidor cuando hace falta.
  • Ciclo de vida y soporte: cada distribución tiene su periodo de soporte y su fin de soporte; las versiones LTS ofrecen ciclos prolongados. Al llegar el fin de vida (EOL) el sistema sigue arrancando, pero deja de recibir parches: vulnerabilidades sin corregir, software que deja de ser compatible y problemas de cumplimiento. Por eso la migración debe planificarse con antelación. Los plazos concretos son dato de actualidad (apartado 10 de Xtra).
🔍 Para ampliar — live patching
Actualizar el kernel normalmente exige reiniciar. Existen mecanismos de live patching (por ejemplo, kpatch en la familia Red Hat o Livepatch de Canonical en Ubuntu) que permiten aplicar determinados parches al núcleo sin reiniciar, retrasando el reinicio a una ventana de mantenimiento. No eliminan todos los reinicios: no cubren todos los parches y suelen depender de la suscripción. Contenido de ampliación.

7. Monitorización

Herramienta Función
top / htop Procesos + consumo de CPU/memoria, en vista interactiva y actualizada
ps Instantánea de los procesos en ejecución
free Memoria RAM + swap; mirar la columna available
df Espacio de los sistemas de archivos (ocupado y libre); df -h legible, df -i inodos
du Espacio ocupado por archivos y directorios; du -sh ruta resume, du -x no sale del sistema de archivos
uptime Tiempo activo + load average (1, 5 y 15 minutos)
ss Conexiones y puertos de red; ss -tuln lista los puertos TCP y UDP en escucha
journalctl Consulta del journal de systemd
/var/log Registros tradicionales en ficheros
⚠️ No confundir comandos — trampa principal del tema
df → espacio del sistema de archivos · du → espacio utilizado por directorios/archivos.
ps → instantánea de procesos · top/htop → visión interactiva y actualizada.
ss → conexiones y puertos · free → memoria · journalctl → journal de systemd.

Leer bien las cifras

  • Memoria: Linux usa la RAM libre como caché (buff/cache) y la devuelve cuando hace falta. Una columna free baja es normal; lo que indica presión es una available baja, junto con uso de swap creciente. Un poco de swap en uso no es por sí solo una avería.
  • Load average: no es un porcentaje de CPU. En Linux cuenta los procesos ejecutándose o esperando CPU y los que esperan E/S de disco. Se interpreta según el número de núcleos: una carga de 4 satura un servidor de un núcleo y es poco para uno de dieciséis. Carga alta con CPU baja suele apuntar a disco o almacenamiento.
  • df y du pueden no cuadrar: un archivo borrado que un proceso mantiene abierto sigue ocupando espacio (lo ve df, no du) hasta que el proceso lo cierra; también influyen los bloques reservados o los montajes.
  • Inodos: cada archivo consume un inodo. Si se agotan (muchos archivos pequeños), no se pueden crear archivos aunque df -h muestre espacio libre: se comprueba con df -i.
  • ss dice si un puerto escucha; no prueba que la aplicación responda bien.

Mini-procedimiento: un servicio no arranca

  • 1. systemctl status servicio — estado, últimos mensajes y si está enabled.
  • 2. journalctl -u servicio — eventos del servicio con más detalle.
  • 3. Comprobar configuración y dependencias (fichero de configuración, unidades de las que depende).
  • 4. Revisar recursos y permisos cuando proceda (espacio, memoria, propietario de ficheros, puertos en uso).
  • 5. Aplicar la actuación autorizada y verificar el servicio real: que el puerto escuche y la aplicación responda. active no es «funciona».

Mini-procedimiento: sistema de archivos lleno

  • 1. df — identificar qué sistema de archivos está lleno.
  • 2. du — localizar qué directorios o archivos ocupan el espacio dentro de ese sistema de archivos.
  • 3. Si df sigue lleno tras borrar, buscar archivos borrados aún abiertos; si df -h muestra espacio pero no se pueden crear archivos, mirar df -i (inodos).
  • 4. Liberar con el procedimiento autorizado (rotación de registros, limpieza de temporales, ampliación del volumen). Nada de rm -rf a ciegas.
🔍 Para ampliar — monitorización centralizada
Para muchos servidores, estas herramientas puntuales se complementan con soluciones que recogen métricas de forma continua y alertan: Nagios, Zabbix o la combinación Prometheus + Grafana (Prometheus recoge métricas y alerta; Grafana las visualiza). Una métrica es un valor medible; un log, un registro de eventos. Una alerta avisa de una condición, no confirma la causa. Su configuración queda fuera del alcance del tema.
