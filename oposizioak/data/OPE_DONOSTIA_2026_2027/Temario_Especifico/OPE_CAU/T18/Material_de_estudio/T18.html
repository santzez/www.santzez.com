1. Notes y Domino: cliente y plataforma

📌 Imprescindible para el examen — la gran pareja del tema
HCL NOTES → el cliente: la aplicación que utiliza la persona usuaria.
HCL DOMINO → la plataforma/servidor que proporciona los servicios y aloja las bases de datos y aplicaciones del ecosistema Notes/Domino.
Domino no es simplemente «un servidor de correo»: es una plataforma de aplicaciones y colaboración que, además, presta servicio de correo.

Evolución (solo como contexto)

  • Lotus Notes — origen del producto.
  • IBM Notes / IBM Domino — etapa bajo IBM.
  • HCL Notes / HCL Domino — etapa bajo HCL, desde 2019.

Los datos de versión, nomenclatura comercial y soporte se recogen, fechados, en el apartado 18.

2. Bases de datos NSF y protocolo NRPC

NSF

  • NSF = Notes Storage Facility: el formato de base de datos nativo utilizado para almacenar datos de Notes/Domino.
  • Correo, aplicaciones y otros datos del ecosistema Domino se almacenan habitualmente en bases de datos NSF.
  • mail.nsf: la base de datos NSF que contiene el buzón de correo del usuario.
📌 Imprescindible para el examen
Una base NSF no tiene por qué ser el buzón. El mail.nsf es una base NSF —la del correo—, pero en un entorno Domino conviven muchas otras: aplicaciones de gestión, directorios, plantillas... Confundir «NSF» con «correo» es una trampa habitual.

NRPC

  • NRPC = Notes Remote Procedure Call: el protocolo nativo/propietario mediante el cual el cliente Notes se comunica con Domino para muchas de sus operaciones.
  • Domino también admite protocolos estándar (SMTP, IMAP, POP3) para interoperabilidad con el resto del ecosistema de correo — su funcionamiento se estudia en el Tema 17.
🧠 Para memorizar
NRPC → NOTES ↔ DOMINO. Es la vía nativa; SMTP/IMAP/POP3 son la vía estándar de interoperabilidad.

3. Replicación y réplicas locales

📌 Imprescindible para el examen — el rasgo más característico
REPLICACIÓN → mecanismo que mantiene sincronizadas distintas réplicas de una base NSF.
Casos típicos: servidor ↔ servidor y servidor ↔ réplica local en el equipo del usuario.
La sincronización es bidireccional: los cambios hechos en cualquiera de las réplicas se propagan a las demás.

Réplica local y trabajo sin conexión

  • La réplica local es una copia de la base NSF en el propio equipo, que permite trabajar con datos y aplicaciones sin conexión y sincronizar los cambios cuando vuelve la conectividad.
  • Matiz: no todas las aplicaciones ni todas las configuraciones funcionarán offline exactamente igual que en línea; depende del diseño de cada base y de los servicios que necesite.
⚠️ No confundir — REPLICACIÓN ≠ BACKUP
La replicación sincroniza réplicas: si un dato se borra o se corrompe en una y se replica, el cambio se propaga a las demás. Una copia de seguridad persigue algo distinto: conservar un estado anterior recuperable. Presentar la replicación como una copia de seguridad es un error conceptual clásico.

4. Identidad y configuración: ID file, Notes.ini e ID Vault

Archivo ID (.id)

  • El ID file es el archivo que contiene la información de identidad y las credenciales criptográficas utilizadas por Notes para autenticar al usuario y realizar operaciones de firma y cifrado.
  • Precisión: no debe definirse simplemente como «un certificado personal». Cumple funciones de identidad y credenciales más amplias que las de un simple certificado.

Contraseña de Notes

📌 Imprescindible para el examen — gran trampa
La contraseña de Notes protege el acceso al archivo ID local.
Contraseña de Notes ≠ contraseña de dominio Windows.
Consecuencia práctica para el CAU: «restablecer la contraseña del usuario» en el dominio no resuelve un olvido de la contraseña del ID.

ID Vault

  • ID Vault: mecanismo centralizado de gestión y recuperación de archivos ID.
  • Ante un olvido de contraseña del ID, se sigue el procedimiento corporativo de recuperación mediante ID Vault o la reexpedición del ID. No es un procedimiento universal idéntico en todas las organizaciones: depende de cómo esté implantado.

Notes.ini

  • Notes.ini: archivo de configuración del cliente Notes, que almacena parámetros de funcionamiento: configuración general, ubicación de los datos, servidor de correo y otros parámetros.
🧠 Para memorizar
NOTES.INI → CONFIGURACIÓN · ID FILE → IDENTIDAD. Uno dice cómo está configurado el cliente; el otro, quién es el usuario.

5. El Directory / Address Book

  • El Directory / Address Book es la base de datos o directorio del entorno Domino que contiene información sobre usuarios, grupos, recursos y configuración del entorno.
⚠️ No confundir
El Directory de Domino desempeña algunas funciones de directorio corporativo, pero no es Active Directory (Tema 12). Son productos y modelos distintos: equipararlos es un error frecuente.

6. Configuración del cliente Notes

Procedimiento general (no depende de una versión concreta):

  • 1. Instalar el cliente Notes en el equipo.
  • 2. Registrar/activar el ID del usuario, con su contraseña.
  • 3. Identificar el servidor Domino al que debe conectarse.
  • 4. Configurar o localizar la base de correo (habitualmente mail.nsf) del usuario.
  • 5. Comprobar el acceso al buzón y a las aplicaciones necesarias.
  • 6. Verificar la replicación cuando proceda (réplicas locales configuradas y sincronizando).

7. Funcionalidades del cliente

  • Correo, calendario, tareas y contactos.
  • Aplicaciones Notes alojadas en bases NSF.
  • Réplica local para trabajo sin conexión.
  • Firma digital y cifrado del correo.

Aplicaciones Notes

Notes/Domino no es solo correo: puede alojar aplicaciones colaborativas desarrolladas sobre bases NSF — por ejemplo, gestión de expedientes, formularios, flujos de aprobación y otras aplicaciones internas. En muchas administraciones, buena parte del uso de la plataforma corresponde a estas aplicaciones a medida, no al buzón. (El desarrollo sobre Domino queda fuera del alcance de este tema.)

Firma y cifrado

Notes permite firmar digitalmente y cifrar correo utilizando la identidad y credenciales del ID file. Los fundamentos de criptografía se estudian en el Tema 24.

8. Acceso mediante interfaz web: iNotes

  • iNotes: interfaz web de acceso al correo, calendario y contactos de Domino, sin necesidad de utilizar el cliente Notes de escritorio.
  • Denominación anterior: Domino Web Access (DWA).
  • Se accede desde un navegador web compatible; el servicio lo presta el propio servidor Domino.
  • Uso típico en el CAU: consultar el correo desde un equipo donde no está instalado ni configurado el cliente Notes, o para un acceso puntual.

10. Datos y anclas de memoria

  • NOTES → CLIENTE · DOMINO → SERVIDOR/PLATAFORMA.
  • NSF → BASE DE DATOS (Notes Storage Facility) · mail.nsf → BUZÓN. Una base NSF no tiene por qué ser el correo.
  • NRPC → NOTES ↔ DOMINO (protocolo nativo); Domino admite además SMTP/IMAP/POP3 para interoperar.
  • REPLICACIÓN → RÉPLICAS SINCRONIZADAS (servidor↔servidor y servidor↔local) · RÉPLICA LOCAL → OFFLINE.
  • REPLICACIÓN ≠ BACKUP.
  • ID → IDENTIDAD (identidad + credenciales criptográficas; no es «solo un certificado») · Notes.ini → CONFIGURACIÓN.
  • Contraseña de Notes ≠ contraseña de dominio: protege el ID local.
  • ID Vault → RECUPERACIÓN DEL ID (según el procedimiento corporativo).
  • Directory = usuarios, grupos, recursos y configuración del entorno Domino — no es Active Directory.
  • iNotes → WEB (antes DWA) · Traveler → MÓVIL/SINCRONIZACIÓN · Verse → CLIENTE MODERNO.
  • Evolución: Lotus → IBM → HCL (2019).

12. Posibles trampas de examen

  • «Notes y Domino son dos nombres del mismo producto» — falso: cliente y plataforma/servidor.
  • «Domino es un servidor de correo» — reduccionista: es una plataforma que aloja bases y aplicaciones, y además presta correo.
  • «Todo NSF es el buzón del usuario» — falso: mail.nsf es una NSF concreta; hay muchas otras (aplicaciones, directorios).
  • «Absolutamente todo en Notes/Domino se almacena en NSF» — formulación excesiva: correo, aplicaciones y otros datos se almacenan habitualmente en NSF.
  • «Una réplica es una copia de seguridad» — falso: la replicación sincroniza; el backup conserva un estado recuperable.
  • «NRPC es el nombre que da Notes a SMTP» — falso: NRPC es el protocolo nativo Notes-Domino; SMTP es estándar.
  • «El ID file es un certificado personal» — impreciso: contiene identidad y credenciales criptográficas, con funciones más amplias.
  • «Restableciendo la contraseña de dominio se soluciona el olvido de la contraseña de Notes» — falso: la del ID es independiente; se recurre a ID Vault o a la reexpedición del ID.
  • «Notes.ini guarda la identidad del usuario» — falso: guarda configuración; la identidad está en el ID file.
  • «El Directory de Domino es Active Directory» — falso: cumple algunas funciones de directorio, pero no lo es.
  • «iNotes es el cliente de escritorio» — falso: es la interfaz web (antes DWA).
  • «Traveler e iNotes son lo mismo» — falso: sincronización con el dispositivo vs. acceso por navegador.
  • «Verse es el servicio que sincroniza los móviles» — falso: eso es Traveler; Verse es un cliente/interfaz moderna.
  • «Con réplica local todo funciona igual sin conexión» — matiz: no todas las aplicaciones y configuraciones se comportan igual offline.

14. Posibles preguntas cortas (con esquema de respuesta)

1. Diferencie Notes y Domino

  • Notes: cliente utilizado por la persona usuaria.
  • Domino: plataforma/servidor que presta servicios y aloja bases de datos y aplicaciones.
  • Cierre: Domino no es solo correo; de ahí la permanencia de la plataforma en muchas organizaciones.

2. Explique qué es una base NSF

  • Definición: Notes Storage Facility, formato de base de datos nativo del ecosistema.
  • Qué se almacena habitualmente en NSF: correo, aplicaciones y otros datos.
  • Cierre: una NSF no tiene por qué ser el buzón.

3. Explique mail.nsf

  • Definición: base NSF que contiene el buzón de correo del usuario.
  • Relación con la configuración del cliente (servidor de correo + base de correo).
  • Cierre: distinguirla de otras NSF (aplicaciones, directorio).

4. Explique NRPC

  • Definición: protocolo nativo/propietario de comunicación entre cliente Notes y Domino.
  • Complemento: Domino admite SMTP/IMAP/POP3 para interoperabilidad.
  • Cierre: no confundir la vía nativa con los estándares del Tema 17.

5. Explique la replicación y las réplicas locales

  • Definición: mecanismo que mantiene sincronizadas réplicas de una base NSF.
  • Casos: servidor ↔ servidor y servidor ↔ réplica local.
  • Réplica local: trabajo sin conexión y sincronización posterior, con el matiz de que no todo se comporta igual offline.
  • Cierre: replicación ≠ backup.

6. Explique el ID file

  • Definición: archivo con la información de identidad y credenciales criptográficas del usuario.
  • Usos: autenticación frente a Domino y operaciones de firma y cifrado.
  • Protección por contraseña propia (distinta de la de dominio) y recuperación mediante ID Vault.

7. Diferencie ID file y Notes.ini

  • ID file: identidad y credenciales.
  • Notes.ini: parámetros de configuración del cliente (ubicación de datos, servidor de correo, otros).
  • Cierre: consecuencia práctica en el diagnóstico de incidencias.

8. Explique iNotes

  • Definición: interfaz web de acceso al correo, calendario y contactos de Domino.
  • Denominación anterior (Domino Web Access) y acceso desde navegador compatible.
  • Cierre: útil cuando no hay cliente Notes instalado.

9. Explique las alternativas de acceso móvil

  • HCL Traveler: sincronización de correo, calendario y contactos con el dispositivo.
  • iNotes desde el navegador móvil: sin instalar aplicación.
  • HCL Verse: cliente/interfaz moderna.
  • Cierre: la gestión del dispositivo (MDM) corresponde al Tema 30.

15. Supuestos prácticos CAU

Supuesto 1 — «He olvidado la contraseña de Notes»

Escenario: un usuario no puede abrir Notes porque no recuerda su contraseña. Pide que «se la reseteen como la del ordenador».

  • a) ¿Por qué no sirve restablecer la del dominio? Porque la contraseña de Notes protege su archivo ID local y es independiente de la contraseña de dominio Windows.
  • b) ¿Qué procede? Seguir el procedimiento corporativo de recuperación: ID Vault o reexpedición del ID, según esté implantado en la organización.
  • c) ¿Es igual en todas las organizaciones? No: depende de cómo esté configurada la gestión de identidades de Domino.

Supuesto 2 — Notes no conecta con Domino

Escenario: tras cambiar el equipo a un usuario, el cliente Notes no consigue conectar con el servidor.

  • a) ¿Qué comprobar? La configuración del cliente (parámetros de Notes.ini: servidor de correo, ubicación de datos), el servidor Domino indicado, la conectividad de red y la identidad (ID correcto y accesible).
  • b) ¿Qué distingue este caso del anterior? Aquí puede fallar la configuración o la red; en el anterior, la credencial del ID. Notes.ini = configuración · ID = identidad.
  • c) ¿Qué protocolo interviene en la conexión nativa? NRPC, entre el cliente Notes y Domino.

Supuesto 3 — Trabajar sin conexión

Escenario: una persona debe desplazarse a una sede sin acceso a la red corporativa y necesita seguir consultando y redactando correo.

  • a) ¿Qué comprobar antes del desplazamiento? Que tenga configurada y sincronizada su réplica local del correo (y de las aplicaciones que necesite).
  • b) ¿Qué ocurre al volver? La replicación sincroniza los cambios en ambos sentidos con el servidor.
  • c) ¿Qué advertir al usuario? Que no todas las aplicaciones ni configuraciones funcionan offline exactamente igual que en línea.

Supuesto 4 — Una NSF que no es el buzón

Escenario: un usuario informa de un problema al abrir «una base de datos de Notes» que no es su correo.

  • a) ¿De qué puede tratarse? De una aplicación Notes alojada en una base NSF: gestión de expedientes, formularios, flujos de aprobación u otra aplicación interna.
  • b) ¿Qué concepto se evalúa? Que una base NSF no tiene por qué ser el buzón: Domino aloja aplicaciones además del correo.
  • c) ¿Qué implica para el diagnóstico? Que el acceso, los permisos y las réplicas de esa base pueden ser distintos de los del mail.nsf.

Supuesto 5 — Consultar el correo desde un equipo ajeno

Escenario: una persona necesita revisar su correo desde un equipo prestado donde no está instalado ni configurado Notes.

  • a) ¿Qué opción encaja? iNotes: interfaz web de acceso al correo, calendario y contactos desde un navegador compatible, sin cliente de escritorio.
  • b) ¿Cómo se denominaba antes? Domino Web Access (DWA).
  • c) ¿Qué evita esta vía? Instalar el cliente y registrar el ID en un equipo que no es el suyo.

Supuesto 6 — Correo y agenda en el móvil

Escenario: se solicita que el correo, el calendario y los contactos estén disponibles y actualizados en el teléfono corporativo.

  • a) ¿Qué componente lo proporciona? HCL Traveler, que sincroniza correo, calendario y contactos entre Domino y el dispositivo.
  • b) ¿Alternativa sin instalar aplicación? Acceder a iNotes desde el navegador del móvil.
  • c) ¿Y la gestión del propio terminal? Corresponde a la movilidad y el MDM (Tema 30), no a este tema.

Supuesto 7 — Interfaz moderna de correo

Escenario: la organización valora ofrecer una experiencia de correo más actual sobre su plataforma Domino.

  • a) ¿Qué producto entra en juego? HCL Verse, cliente/interfaz moderna de correo y colaboración.
  • b) ¿Sustituye a Traveler? No: son cosas distintas — Verse es interfaz de usuario; Traveler es sincronización con dispositivos.
  • c) ¿Y a iNotes? Verse es una alternativa más moderna de acceso; iNotes sigue siendo la interfaz web clásica de Domino.

17. Resumen final: si mañana fuera el examen

  • Notes = cliente · Domino = plataforma/servidor que aloja bases y aplicaciones (no solo correo). Evolución: Lotus → IBM → HCL (2019).
  • NSF = formato de base de datos nativo; correo, aplicaciones y otros datos se almacenan habitualmente en NSF. mail.nsf = buzón, pero una NSF no tiene por qué ser el correo.
  • NRPC = protocolo nativo Notes ↔ Domino; Domino admite además SMTP/IMAP/POP3 para interoperar (Tema 17).
  • Replicación = sincronización de réplicas de una NSF (servidor↔servidor y servidor↔local). La réplica local permite trabajar sin conexión y sincronizar después — con el matiz de que no todo funciona igual offline. Replicación ≠ backup.
  • ID file = identidad + credenciales criptográficas (autenticación, firma, cifrado): no es simplemente un certificado. Su contraseña protege el ID local y no es la del dominio. ID Vault = recuperación centralizada. Notes.ini = configuración.
  • Directory / Address Book = usuarios, grupos, recursos y configuración del entorno Domino; no es Active Directory.
  • Configuración del cliente: instalar → registrar el ID → identificar el servidor Domino → configurar la base de correo → comprobar acceso → verificar replicación.
  • Funcionalidades: correo, calendario, tareas, contactos, aplicaciones NSF, réplica local, firma y cifrado con el ID.
  • Accesos: iNotes (web, antes DWA, navegador compatible) · Traveler (sincronización con móviles) · Verse (cliente/interfaz moderna). No confundirlos entre sí.

18. Actualidad HCL Notes/Domino — datos fechados

📌 Información sujeta a cambio · Fecha de actualización de estos apuntes: agosto de 2026
Versiones, nomenclatura comercial y plazos de soporte evolucionan; el núcleo conceptual del tema no depende de estos datos.
  • Propiedad: el producto pertenece a HCL desde 2019, tras su adquisición a IBM. En muchas organizaciones se sigue hablando indistintamente de «IBM Notes» y «HCL Notes».
  • Nomenclatura: HCL ha adoptado una denominación por año para las versiones recientes de Notes/Domino, además de la numeración de build tradicional.
  • Ciclo de soporte: HCL ha publicado compromisos de soporte para versiones actuales y anteriores; conviene consultar el ciclo vigente antes de planificar migraciones.
  • Contexto de uso: la plataforma mantiene una implantación significativa en grandes organizaciones y administraciones, en buena medida por las aplicaciones a medida desarrolladas sobre bases NSF, cuya migración resulta costosa.
