1. Base de datos y SGBD: del fichero a la gestión de datos

En el Tema 4 vimos los ficheros como forma de almacenar información, cada uno gestionado por sus aplicaciones individuales. Cuando varias aplicaciones necesitan compartir datos, ese esquema da problemas: la misma información se duplica (redundancia), las copias se desincronizan (inconsistencia) y resulta difícil controlar accesos y escrituras simultáneas. La base de datos con su SGBD supone el salto conceptual: una gestión más estructurada y administrada de los datos, compartida entre aplicaciones.

📌 Imprescindible para el examen
Base de datos: conjunto organizado de datos relacionados, gestionados de forma que puedan ser utilizados por aplicaciones y usuarios. Su arquitectura puede ser centralizada o distribuida: la centralización no forma parte de la definición.
SGBD (Sistema Gestor de Bases de Datos, DBMS): el software que permite crear, gestionar, consultar y controlar el acceso a bases de datos, actuando de intermediario entre las aplicaciones y los datos. SGBD ≠ base de datos: uno es el software; la otra, los datos.

Ventajas frente a los ficheros independientes

  • Reducción de la redundancia: los datos se almacenan de forma controlada y se comparten entre aplicaciones.
  • Integridad y consistencia: el SGBD puede aplicar reglas que evitan datos contradictorios.
  • Control de acceso: puede definirse quién accede a qué información y con qué permisos.
  • Concurrencia: varios usuarios o procesos pueden trabajar a la vez de forma controlada.
  • Independencia entre datos y aplicaciones: los programas no necesitan conocer el almacenamiento físico de los datos.

Estas propiedades no son garantías automáticas de cualquier SGBD: dependen del diseño, la configuración y las capacidades concretas de cada sistema.

🔍 Para ampliar — contexto útil, menor probabilidad de pregunta directa
SGBD relacionales muy extendidos: Oracle Database, Microsoft SQL Server, MySQL, MariaDB, PostgreSQL y, como base de datos ligera embebida, SQLite. En entornos corporativos el SGBD suele funcionar en modo cliente-servidor: la base de datos reside en un servidor y las aplicaciones se conectan por red. No es necesario memorizar productos.

2. Tipos de bases de datos

  • Jerárquica: organiza los datos en forma de árbol, con relaciones padre-hijo (cada hijo tiene un único padre).
  • En red: similar, pero permite que un registro tenga varios «padres», representando relaciones más complejas.
  • Relacional: organiza los datos en tablas vinculadas mediante claves. Es el modelo más extendido y el que desarrolla el resto del tema — prioridad máxima.
  • Orientada a objetos: almacena los datos como objetos, con sus atributos y comportamiento, en coherencia con la programación orientada a objetos.
  • NoSQL («Not Only SQL»): familia de enfoques no relacionales, pensados para grandes volúmenes, alta disponibilidad y esquemas flexibles. No es un único modelo.
🧠 Para memorizar
Jerárquica = árbol, un solo padre · En red = varios padres · Relacional = tablas + claves · Objetos = atributos y comportamiento · NoSQL = familia de alternativas. Como ejemplo de familias NoSQL (sin memorizar productos): clave-valor, documental, columnar y de grafos.

3. El modelo relacional: conceptos básicos

El modelo relacional fue propuesto por Edgar F. Codd en 1970 (dato de contexto susceptible de pregunta) y representa toda la información mediante tablas, cada una dedicada a un tipo de entidad («empleados», «departamentos»).

  • Tabla (o relación): estructura bidimensional que almacena los datos de una entidad, organizados en filas y columnas.
  • Fila (o tupla): cada una de las ocurrencias concretas almacenadas en la tabla.
  • Columna (o atributo): cada una de las características que describen a la entidad.
  • Dominio: el conjunto de valores posibles o permitidos para un atributo. Ejemplo: el dominio del atributo «mes» son los valores 1 a 12; el del atributo «letra del NIF», las letras válidas del algoritmo.
  • NULL: representa la ausencia de un valor en un atributo; su significado concreto depende del contexto (puede no conocerse el valor, no ser aplicable, no haberse introducido aún...).
📌 Imprescindible para el examen — NULL
NULL ≠ 0 y NULL ≠ cadena vacía. Cero y «cadena vacía» son valores; NULL es la ausencia de valor. Trampa clásica de test.
🧠 Para memorizar — analogía didáctica con el Tema 4
TABLA ≈ fichero · FILA/TUPLA ≈ registro · COLUMNA/ATRIBUTO ≈ campo.
Es una analogía para estudiar, no una equivalencia conceptual absoluta: la tabla relacional añade restricciones, integridad y relaciones que un fichero no tiene. Los emparejamientos «tupla-fila» y «atributo-columna» son pregunta directa de test.

4. Claves, integridad y relaciones entre tablas

Claves

  • Clave candidata: atributo o conjunto de atributos que podría identificar unívocamente cada fila (en EMPLEADOS: el DNI y el número de empleado son candidatas).
  • Clave primaria (PK — Primary Key): la candidata elegida para identificar de forma única cada fila.
  • Clave foránea (o ajena, FK — Foreign Key): atributo o conjunto de atributos que referencia la clave de otra tabla (o de la misma) y permite establecer relaciones.

Integridad

Regla Qué garantiza Sobre qué clave actúa
Integridad de entidad La clave primaria identifica inequívocamente cada fila: no puede repetirse y no debe admitir NULL PK
Integridad referencial Toda referencia mediante clave foránea es coherente con la clave referenciada, conforme a las reglas establecidas (el valor existe en la tabla referenciada, o queda sin valor si se permite) FK
💡 Ejemplo
En una base de datos municipal: EMPLEADOS tiene como PK el número de empleado y una FK «código de departamento» que apunta a la PK de DEPARTAMENTOS. La integridad referencial impide asignar a alguien un departamento inexistente, y las reglas establecidas determinan qué ocurre si se intenta borrar un departamento con personal asignado.

Tipos de relación entre tablas (prioridad de memorización)

  • Uno a uno (1:1): cada fila de una tabla se relaciona con, como mucho, una fila de la otra (un empleado ↔ su credencial personal única).
  • Uno a muchos (1:N): una fila puede relacionarse con varias de la otra tabla, pero no al revés. Ejemplo municipal: un DEPARTAMENTO tiene muchos EMPLEADOS, y cada empleado pertenece a un único departamento — la FK «departamento» vive en EMPLEADOS.
  • Muchos a muchos (N:M): varias filas de cada tabla se relacionan entre sí. Ejemplo: un EMPLEADO realiza varios CURSOS y cada curso lo realizan varios empleados.
📌 Imprescindible para el examen
La relación N:M no puede representarse directamente en el modelo relacional: se implementa mediante una tabla intermedia que incorpora las claves necesarias de ambas tablas. EMPLEADOS ↔ CURSOS se resuelve con la tabla EMPLEADO-CURSO (FK a empleado + FK a curso). Es uno de los detalles más preguntados del tema.

5. Estándares de conectividad: ODBC y JDBC

El enunciado oficial cita expresamente los estándares de conectividad: son un bloque principal del tema. El problema que resuelven: una aplicación necesita acceder a bases de datos sin quedar atada a un SGBD concreto. La solución es una arquitectura de dos piezas:

  • API (interfaz de programación): el conjunto común y estandarizado de funciones que la aplicación utiliza para conectarse, consultar y modificar datos — el mismo sea cual sea el motor.
  • Driver (controlador): el componente específico de cada SGBD que traduce esas llamadas comunes a las particularidades del motor concreto.

Resultado: independencia respecto del SGBD — cambiar de motor implica, en lo esencial, cambiar de driver, no reescribir la aplicación.

ODBC

  • ODBC (Open Database Connectivity): estándar/API de conectividad de propósito general con SGBD mediante drivers. La aplicación usa la interfaz común ODBC y el driver se ocupa de las particularidades del motor.
  • Ejemplo práctico CAU: en los equipos Windows corporativos, los orígenes de datos ODBC (DSN) se configuran desde el «Administrador de orígenes de datos ODBC» — algo que un técnico puede encontrarse al instalar o reparar aplicaciones que consultan bases de datos.

JDBC

  • JDBC (Java Database Connectivity): la API estándar de Java para acceder a bases de datos mediante drivers JDBC, con la misma filosofía (API común + driver por motor) aplicada al ecosistema Java.
ODBC JDBC
Finalidad Conectividad general con SGBD Conectividad con SGBD desde Java
API ODBC (interfaz común) JDBC (API de Java)
Driver Específico para cada SGBD Específico para cada SGBD
Asociado especialmente a Aplicaciones generales (p. ej., configurables vía DSN en Windows) Aplicaciones Java
🧠 Para memorizar
ODBC → conectividad general · JDBC → Java. Ambos: API común + driver específico del SGBD. Si la pregunta menciona Java, la respuesta es JDBC.
🔍 Para ampliar — contexto útil, menor probabilidad de pregunta directa
Muchas aplicaciones actuales añaden por encima una capa de ORM (mapeo objeto-relacional), y han existido puentes ODBC-JDBC. No hace falta profundizar para este tema.

6. Ampliación: SQL básico y transacciones (ACID)

Ampliación útil relacionada con el uso de bases de datos relacionales — contenido secundario frente al modelo relacional y la conectividad.

SQL: los tres grupos de sentencias

SQL (Structured Query Language) es el lenguaje estándar para definir, consultar y manipular bases de datos relacionales. Sin dominar sintaxis, conviene reconocer sus tres grupos:

Grupo Para qué sirve Sentencias típicas
DDL (Data Definition Language) Definir la estructura (tablas, índices) CREATE, ALTER, DROP
DML (Data Manipulation Language) Consultar y manipular los datos SELECT, INSERT, UPDATE, DELETE
DCL (Data Control Language) Controlar permisos de acceso GRANT, REVOKE

Transacciones y propiedades ACID

Una transacción es un conjunto de operaciones que se ejecuta como unidad indivisible: o se completan todas, o no se aplica ninguna (el ejemplo clásico: una transferencia que resta de una cuenta y suma en otra). Las propiedades ACID:

  • Atomicidad: todo o nada.
  • Consistencia: de un estado válido a otro estado válido, respetando las reglas de integridad.
  • Aislamiento (Isolation): las transacciones concurrentes no interfieren entre sí.
  • Durabilidad: una vez confirmada (commit), persiste aunque el sistema falle después.

7. Datos y anclas de memoria

  • TABLA → filas + columnas · FILA → tupla · COLUMNA → atributo (analogía con T4: ≈ fichero/registro/campo).
  • PK → identifica · FK → relaciona.
  • Integridad de ENTIDAD → PK (única, sin NULL) · REFERENCIAL → FK (referencia coherente).
  • 1:N → un padre, muchos hijos · N:M → tabla intermedia (siempre).
  • NULL = ausencia de valor (≠ 0, ≠ cadena vacía); su significado depende del contexto.
  • Dominio = valores permitidos de un atributo.
  • ODBC → general · JDBC → Java; ambos = API común + driver específico.
  • DDL → define · DML → manipula · DCL → controla.
  • ACID = Atomicidad · Consistencia · Aislamiento · Durabilidad.
  • Modelo relacional: Codd, 1970.
  • Tipos: jerárquica (árbol) · en red (varios padres) · relacional (tablas) · objetos · NoSQL (familia).

9. Posibles trampas de examen

  • «NULL equivale a 0» o «NULL es la cadena vacía» — falso: NULL es ausencia de valor; 0 y «» son valores.
  • «La clave foránea identifica de forma única cada fila» — falso: eso es la PK; la FK relaciona tablas y puede repetirse.
  • «La integridad referencial exige que la PK no sea nula» — cruce de conceptos: eso es la integridad de entidad; la referencial afecta a las FK.
  • «Una relación N:M se implementa con una FK en una de las dos tablas» — falso: exige tabla intermedia.
  • «ODBC es el estándar de conectividad de Java» — invertido: el de Java es JDBC; ODBC es de propósito general.
  • «DDL sirve para insertar y modificar datos» — falso: DDL define estructura; manipular datos es DML.
  • «DCL agrupa las sentencias de consulta» — falso: DCL controla permisos (GRANT/REVOKE); SELECT es DML.
  • «Una base de datos es, por definición, centralizada» — falso: puede ser centralizada o distribuida.
  • «NoSQL es un modelo concreto de base de datos» — falso: es una familia de enfoques no relacionales (clave-valor, documental, columnar, grafos).
  • «SGBD y base de datos son sinónimos» — falso: software gestor vs. conjunto de datos.
  • «Toda clave candidata es la clave primaria» — falso: la PK es la candidata elegida; puede haber varias candidatas.
  • «El driver es igual para todos los SGBD» — falso: la API es común; el driver es específico de cada motor.

11. Posibles preguntas cortas (con esquema de respuesta)

1. Explique qué es una base de datos y qué función cumple un SGBD

  • Definición de base de datos (datos organizados y relacionados; arquitectura centralizada o distribuida).
  • Definición de SGBD (software intermediario: crear, gestionar, consultar, controlar el acceso).
  • Ventajas frente a ficheros: redundancia, integridad, control de acceso, concurrencia, independencia — señalando que dependen del diseño y configuración.

2. Explique los conceptos básicos del modelo relacional

  • Origen (Codd, 1970) e idea central: todo en tablas.
  • Tabla/relación, fila/tupla, columna/atributo, dominio, NULL — una frase por concepto.
  • Cierre: la analogía didáctica con fichero/registro/campo del Tema 4.

3. Diferencie clave candidata, primaria y foránea

  • Candidata: podría identificar unívocamente. Primaria: la elegida (única, sin NULL). Foránea: referencia la clave de otra tabla.
  • Acrónimos PK/FK y ejemplo (número de empleado como PK; código de departamento como FK).

4. Explique la integridad de entidad y la integridad referencial

  • Entidad: la PK identifica inequívocamente y no admite NULL.
  • Referencial: las FK deben ser coherentes con la clave referenciada, según las reglas establecidas.
  • Ejemplo municipal (no asignar departamentos inexistentes).

5. Explique los tipos de relaciones entre tablas

  • 1:1, 1:N y N:M, con un ejemplo de cada (credencial · departamento-empleados · empleados-cursos).
  • Dónde vive la FK en la 1:N; la tabla intermedia como implementación obligada de la N:M.

6. Explique qué son ODBC y JDBC y sus diferencias

  • El problema: independencia respecto del SGBD. La arquitectura: API común + driver específico.
  • ODBC: estándar general (DSN en Windows como ejemplo práctico). JDBC: API de Java.
  • Cierre: la regla «Java → JDBC»; en lo demás, misma filosofía.

12. Supuestos prácticos

Supuesto 1 — Empleados, departamentos y cursos

Escenario: una aplicación municipal debe gestionar empleados, departamentos y cursos de formación. Cada empleado pertenece a un departamento; cada empleado puede realizar varios cursos y cada curso lo realizan varios empleados.

  • a) ¿Qué tablas hacen falta y con qué PK? EMPLEADOS (PK: número de empleado), DEPARTAMENTOS (PK: código de departamento), CURSOS (PK: código de curso) — y una cuarta, intermedia, para la relación N:M.
  • b) ¿Cómo se modela «cada empleado pertenece a un departamento»? Relación 1:N: FK «código de departamento» en la tabla EMPLEADOS, apuntando a la PK de DEPARTAMENTOS.
  • c) ¿Y «empleados realizan cursos»? Relación N:M → tabla intermedia EMPLEADO-CURSO con FK al empleado y FK al curso (juntas pueden formar su PK).
  • d) ¿Qué protege la integridad referencial aquí? Que no se asigne un departamento o un curso inexistente, y que el borrado de un departamento o curso con referencias se resuelva conforme a las reglas establecidas.

Supuesto 2 — Conectividad estándar

Escenario: una aplicación de escritorio Windows del ayuntamiento debe consultar datos que hoy están en un SGBD y que el año próximo migrarán a otro motor distinto.

  • a) ¿Qué estándar podría utilizar y por qué? ODBC: la aplicación programa contra la API común y no contra el motor concreto, ganando independencia del SGBD.
  • b) ¿Qué función cumple el driver? Traducir las llamadas de la API común a las particularidades del motor; al migrar, se sustituye el driver (y el origen de datos DSN), no la aplicación.
  • c) ¿Cuándo tendría sentido JDBC? Si la aplicación estuviera desarrollada en Java: JDBC es la API estándar de Java para bases de datos, con la misma arquitectura de drivers.

Supuesto 3 — El NULL conflictivo

Escenario: en la tabla EMPLEADOS, la columna «teléfono de contacto» presenta tres situaciones: un empleado con valor «943...», otro con cadena vacía y otro con NULL. Un informe cuenta «empleados sin teléfono» y da resultados extraños.

  • a) ¿Son equivalentes las tres situaciones? No: «943...» es un valor; la cadena vacía también es un valor (vacío); NULL es ausencia de valor, cuyo significado depende del contexto (no facilitado, desconocido...).
  • b) ¿Por qué falla el informe? Si solo cuenta cadenas vacías (o solo NULL), ignora la otra situación: hay que decidir qué representa «sin teléfono» y tratar ambos casos.
  • c) ¿Qué concepto del tema lo explica? NULL ≠ 0 ≠ cadena vacía — la trampa clásica del modelo relacional.

Supuesto 4 — Elegir el tipo de base de datos

Escenario: se evalúan sistemas para tres necesidades: (1) expedientes con estructura tabular estable y relaciones claras; (2) un catálogo de documentos con estructura muy variable; (3) representar la red de relaciones entre entidades municipales.

  • a) Asigna el modelo adecuado a cada caso. (1) Relacional: tablas, claves e integridad. (2) NoSQL documental: esquema flexible. (3) NoSQL de grafos: nodos y relaciones.
  • b) ¿Qué debe recordarse de NoSQL? Que no es un modelo único sino una familia (clave-valor, documental, columnar, grafos), y que el relacional sigue siendo el dominante para datos estructurados con relaciones.

14. Resumen final: si mañana fuera el examen

  • Base de datos = datos organizados y relacionados (centralizada o distribuida) · SGBD = el software que los gestiona. Ventajas frente a ficheros: redundancia, integridad, control de acceso, concurrencia, independencia — según diseño y configuración.
  • Tipos: jerárquica (árbol, un padre) · en red (varios padres) · relacional (dominante) · orientada a objetos · NoSQL (familia: clave-valor, documental, columnar, grafos).
  • Modelo relacional (Codd, 1970): tabla/relación · fila/tupla · columna/atributo · dominio (valores permitidos) · NULL = ausencia de valor ≠ 0 ≠ cadena vacía. Analogía didáctica con T4: tabla ≈ fichero, fila ≈ registro, columna ≈ campo.
  • Claves: candidata (podría) → PK (elegida; única, sin NULL) · FK (referencia y relaciona). Integridad de entidad → PK · referencial → FK.
  • Relaciones: 1:1 · 1:N (FK en el lado «muchos»; departamento-empleados) · N:M → tabla intermedia (empleados-cursos).
  • Conectividad (bloque principal): el problema es la independencia del SGBD; la solución, API común + driver específico. ODBC = general (DSN en Windows) · JDBC = Java.
  • Ampliación: SQL — DDL define (CREATE/ALTER/DROP) · DML manipula (SELECT/INSERT/UPDATE/DELETE) · DCL controla (GRANT/REVOKE). Transacción = todo o nada; ACID.
