1. Arquitectura y componentes: MUA, MSA, MTA y MDA

El correo electrónico funciona gracias a la cooperación de varios agentes con papeles bien diferenciados. Distinguirlos es el contenido más preguntable del tema.

Componente Nombre completo Función
MUA Mail User Agent Programa o interfaz que utiliza la persona usuaria para redactar, enviar y leer correo
MSA Mail Submission Agent Recibe el correo enviado por el cliente para su submission (entrada) al sistema de correo
MTA Mail Transfer Agent Transporta y encamina los mensajes entre servidores mediante SMTP
MDA Mail Delivery Agent Entrega el mensaje en el buzón del destinatario
🧠 Para memorizar — gran ancla del tema
MUA → USA · MSA → RECIBE EL ENVÍO DEL CLIENTE · MTA → TRANSPORTA · MDA → ENTREGA.
Es una regla de memoria, no una definición técnica: para responder con rigor, apóyate en la tabla anterior.

El MSA se introduce aquí sobre todo porque explica la razón de ser del puerto 587 (apartado 4): separar el envío del cliente (submission, normalmente autenticado) del transporte entre servidores (relay). En muchas implementaciones el MSA y el MTA forman parte del mismo producto.

2. El registro MX y el recorrido del mensaje

Registro MX

  • MX = Mail Exchanger: registro DNS que indica qué servidor o servidores reciben el correo de un dominio.
  • Admite varios servidores con distinta prioridad: se intenta primero el de valor de preferencia más bajo y, si no responde, los siguientes — mecanismo básico de respaldo.
🧠 Para memorizar
MX → «¿dónde recibe correo este dominio?». Ojo: el MX no es el servidor de correo, es el registro DNS que permite localizarlo.

Recorrido del mensaje (modelo de estudio)

MUA → MSA / SMTP submission → MTA → consulta MX → MTA destino → MDA → buzón → POP3/IMAP → MUA destinatario

  • El MUA del remitente entrega el mensaje al MSA (submission, habitualmente autenticada).
  • El MTA de salida consulta el registro MX del dominio de destino para saber a qué servidor dirigirse.
  • El mensaje viaja por SMTP hasta el MTA de destino, que puede no ser el último: puede haber relays intermedios.
  • El MDA deposita el mensaje en el buzón del destinatario.
  • El destinatario accede a su buzón con su MUA mediante POP3 o IMAP.
⚠️ Modelo didáctico, no secuencia rígida
La arquitectura real puede variar: MSA, MTA y MDA pueden estar implementados de formas distintas (integrados en un mismo producto, distribuidos en varios servidores, o sustituidos por servicios en la nube con sus propios flujos internos). El esquema anterior sirve para razonar el recorrido, no como secuencia obligatoria de cualquier plataforma.

3. Estructura del mensaje: cabeceras, cuerpo y MIME

Todo mensaje se compone de cabeceras (headers) y cuerpo.

Cabecera Contenido
From Remitente mostrado del mensaje
To Destinatario o destinatarios principales
Cc Copia: destinatarios visibles para los demás destinatarios
Cco / Bcc Copia oculta: destinatarios ocultos para los demás destinatarios
Subject Asunto
Date Fecha y hora del mensaje
Message-ID Identificador único del mensaje
Received Traza añadida por los servidores/relays que reciben y procesan el mensaje
📌 Imprescindible para el examen — Cc y Cco
Cc → los destinatarios se ven entre sí. Cco/Bcc → los destinatarios en copia oculta no son visibles para los demás. Distinción clásica de test y de uso cotidiano (envíos masivos a la ciudadanía, por ejemplo).

La cabecera Received

Cada servidor o relay que recibe y procesa el mensaje añade su propia línea Received. El conjunto permite reconstruir el recorrido del mensaje.

💡 Caso CAU
Un mensaje no llega a destino: revisar las cabeceras Received permite ver por qué servidores pasó y localizar dónde se interrumpió el recorrido (si salió del servidor propio, si llegó al del destinatario, dónde se detuvo). El análisis forense detallado de cabeceras queda fuera de este tema.

MIME

  • MIME (Multipurpose Internet Mail Extensions): estándar que permite representar contenido no limitado a texto simple dentro de los mensajes de correo.
  • Gracias a MIME un mensaje puede incluir HTML, imágenes, adjuntos y distintos tipos de contenido, e incluso varias partes con formatos diferentes.
⚠️ No confundir — MIME ≠ Base64
MIME es el estándar que estructura y describe el contenido del mensaje. Base64 es una de las codificaciones que pueden utilizarse dentro de MIME para representar contenido binario de forma segura en el transporte. Decir que «MIME es Base64» es un error conceptual.

4. SMTP: envío y transferencia

SMTP (Simple Mail Transfer Protocol) es el protocolo utilizado tanto para el message submission (la entrada del mensaje al sistema desde el cliente) como para la transferencia o relay del correo entre servidores.

📌 Imprescindible para el examen
SMTP → envío/submission + transferencia entre servidores.
POP3 / IMAP → acceso al correo ya entregado en el buzón.
No basta con decir «SMTP solo sirve para enviar»: también es el protocolo del relay entre MTA. Lo que SMTP no hace es permitir a un cliente consultar o descargar su buzón.

Puertos

Puerto Uso
25 SMTP relay entre servidores (MTA a MTA)
587 Message Submission del cliente, normalmente con autenticación y STARTTLS/TLS
465 Message Submission sobre TLS implícito (la conexión se cifra desde el inicio)

Los puertos 587 y 465 no son equivalentes ni un simple duplicado: ambos sirven para la submission del cliente, pero difieren en cómo se establece el cifrado — negociado sobre la conexión (STARTTLS) en el 587, e implícito desde el inicio en el 465.

📌 Actualidad de los protocolos
Las recomendaciones actuales favorecen el uso de TLS tanto para la submission como para el acceso al correo: 587 con STARTTLS/TLS, 465 con TLS implícito, 995 (POP3) y 993 (IMAP) con TLS. Los puertos sin cifrado se citan para reconocerlos, no como recomendación práctica.

5. Acceso al buzón: POP3 e IMAP

POP3

  • POP3 (Post Office Protocol v3): protocolo para descargar o recuperar mensajes desde un servidor de correo.
  • Puertos: 110 (sin TLS) y 995 (con TLS implícito).
⚠️ No confundir — POP3 no borra necesariamente
En la configuración clásica, el cliente puede descargar y eliminar los mensajes del servidor, pero puede configurarse para conservar una copia en él. Afirmar que «POP3 siempre borra el correo del servidor» es incorrecto.
Tampoco es exacto decir que POP3 esté formalmente limitado a un solo dispositivo: lo que ocurre es que su capacidad de sincronización es mucho más limitada que la de IMAP (no sincroniza carpetas ni estados entre clientes).

IMAP

  • IMAP (Internet Message Access Protocol): permite acceder y gestionar los mensajes almacenados en el servidor.
  • Puertos: 143 y 993 (con TLS implícito).
  • Gestiona carpetas, el estado leído/no leído y los propios mensajes, con sincronización entre dispositivos: lo que se hace en uno se refleja en los demás.
🧠 Para memorizar
IMAP → SERVIDOR + SINCRONIZACIÓN · POP3 → DESCARGA.
POP3 IMAP
Modelo Descarga Acceso al buzón remoto
Mensajes Pueden descargarse localmente (y conservarse o no en el servidor) Permanecen en el servidor
Sincronización multidispositivo Limitada Sí
Carpetas y estado Limitado Sincronizados
Puertos 110 / 995 143 / 993

6. Autenticación del dominio: SPF, DKIM y DMARC

SMTP, por diseño, no verifica que quien envía sea quien dice ser. Para mitigarlo existen tres mecanismos complementarios, asociados al dominio remitente. (El spoofing, el spam y el phishing como amenazas se estudian en el Tema 25; la criptografía, en el Tema 24.)

SPF

  • SPF (Sender Policy Framework): mecanismo mediante el cual un dominio publica qué hosts u orígenes están autorizados a enviar correo utilizando ese dominio. La política se publica normalmente en DNS.
  • Precisión importante: SPF no verifica directamente que el campo From visible sea auténtico. Su comprobación se relaciona con la identidad/dominio utilizada durante el envío y con el origen de la conexión.
🧠 Para memorizar
SPF → AUTORIZA SERVIDORES/ORÍGENES de envío del dominio.

DKIM

  • DKIM (DomainKeys Identified Mail): firma criptográfica que permite verificar la autenticidad de la firma y la integridad de los elementos firmados del mensaje.
  • Clave privada → firma (en el lado emisor). Clave pública → se publica en DNS y sirve para verificar.
  • Precisión: DKIM no «certifica al remitente» como prueba absoluta de identidad personal; acredita que el dominio firmante avaló el mensaje y que lo firmado no se ha alterado.
🧠 Para memorizar
DKIM → FIRMA + INTEGRIDAD.

DMARC

  • DMARC (Domain-based Message Authentication, Reporting and Conformance): mecanismo y política que permite al propietario de un dominio indicar cómo tratar los mensajes que no superan las comprobaciones de autenticación y de alineación requeridas.
  • Incorpora la idea de alineación: no basta con que SPF o DKIM pasen; deben además corresponderse con el dominio conforme a la política establecida.
  • Políticas posibles: none (no actuar, solo observar), quarantine (cuarentena) y reject (rechazo).
  • Permite además recibir informes sobre los resultados de esas comprobaciones.
🧠 Para memorizar
DMARC → POLÍTICA + ALINEACIÓN + INFORMES. Reducirlo a «si SPF o DKIM fallan, rechaza» deja fuera lo esencial.
Mecanismo Idea que debo recordar
SPF Autoriza orígenes de envío
DKIM Firma + integridad
DMARC Política + alineación + informes
📌 Imprescindible para el examen — relación con el DNS
No es exacto decir sin más que «SPF, DKIM y DMARC son registros DNS»:
SPF → política publicada en DNS.
DKIM → la firma viaja en el mensaje; lo que se publica en DNS es la clave pública de verificación.
DMARC → política publicada en DNS, normalmente bajo _dmarc.
Distinguir el mecanismo de lo que se publica en DNS es conceptualmente importante.

7. Clientes de correo

Tipo Características Ejemplos
Escritorio Aplicación instalada en el equipo, con configuración de cuentas y almacenamiento local Outlook, Thunderbird, IBM/HCL Notes (Tema 18)
Webmail Acceso desde el navegador mediante HTTP/HTTPS, sin instalar ni configurar cliente OWA, Gmail (plataformas web: Tema 20)
Móvil Aplicaciones de correo del dispositivo, con notificaciones y sincronización Clientes nativos y de proveedores

Protocolos que utiliza un cliente

  • SMTP para el envío (submission).
  • IMAP o POP3 para el acceso al correo recibido.
  • Como ampliación, algunos productos utilizan protocolos propios: por ejemplo, MAPI en el entorno Exchange.
⚠️ No confundir — MAPI
MAPI no es otro nombre de SMTP/IMAP: es un mecanismo distinto, propio del ecosistema Exchange, que ofrece una integración enriquecida (correo, calendario, contactos) más allá de los protocolos estándar. El detalle de Exchange no es objeto de este tema.

8. Datos y anclas de memoria

  • MUA → USA · MSA → SUBMISSION · MTA → TRANSPORTA · MDA → ENTREGA.
  • MX → ¿DÓNDE RECIBE? — registro DNS con prioridad, no el servidor en sí.
  • SMTP → ENVÍA/TRANSPORTA · IMAP → SERVIDOR + SINCRONIZA · POP3 → DESCARGA.
  • Puertos: 25 → RELAY · 587 → SUBMISSION (STARTTLS/TLS) · 465 → SUBMISSION + TLS IMPLÍCITO.
  • 110/995 → POP3 · 143/993 → IMAP (los «9x» son las variantes con TLS implícito).
  • Cabeceras: From · To · Cc (visibles) · Cco/Bcc (ocultos) · Subject · Date · Message-ID · Received (traza del recorrido).
  • MIME = estándar para contenido no limitado a texto simple; Base64 = codificación que puede usarse dentro de MIME.
  • SPF → AUTORIZA · DKIM → FIRMA (+ integridad) · DMARC → POLÍTICA + ALINEACIÓN + INFORMES.
  • DNS: SPF (política) · DKIM (clave pública; la firma va en el mensaje) · DMARC (política, bajo _dmarc).
  • Clientes: escritorio · webmail · móvil; un cliente usa SMTP para enviar e IMAP/POP3 para recibir.

10. Posibles trampas de examen

  • «SMTP se usa para consultar el buzón» — falso: para eso están POP3 e IMAP; SMTP hace submission y transferencia.
  • «POP3 borra siempre los mensajes del servidor» — falso: en la configuración clásica puede descargarlos y eliminarlos, pero puede configurarse para conservar copia.
  • «POP3 solo puede usarse en un dispositivo» — impreciso: lo limitado es su capacidad de sincronización, no una prohibición formal.
  • «IMAP descarga y vacía el buzón» — falso: mantiene los mensajes en el servidor y sincroniza carpetas y estados.
  • «El puerto 25 es el recomendado para que los clientes envíen correo» — falso: el 25 es el de relay entre servidores; la submission del cliente usa 587 (o 465).
  • «587 y 465 son exactamente lo mismo» — falso: ambos son submission, pero difieren en el establecimiento del cifrado (STARTTLS/TLS vs. TLS implícito).
  • «MUA y MTA son sinónimos» — falso: cliente del usuario vs. servidor de transporte.
  • «MTA y MDA son lo mismo» — falso: transportar entre servidores vs. entregar en el buzón.
  • «El MX es el servidor de correo» — falso: es el registro DNS que indica qué servidores reciben el correo del dominio.
  • «MIME es Base64» — falso: Base64 es una codificación que puede usarse dentro de MIME.
  • «SPF verifica que el From visible es auténtico» — falso: SPF autoriza orígenes de envío; su comprobación se relaciona con la identidad/dominio del envío y el origen de la conexión.
  • «DKIM y SPF hacen lo mismo» — falso: DKIM firma y protege la integridad de lo firmado; SPF autoriza orígenes.
  • «DMARC es simplemente rechazar el spam» — falso: define política (none/quarantine/reject), incorpora alineación y aporta informes.
  • «Cc y Cco son equivalentes» — falso: la copia oculta no es visible para el resto de destinatarios.
  • «Webmail y cliente de escritorio son lo mismo» — falso: navegador sin instalación vs. aplicación instalada y configurada.

12. Posibles preguntas cortas (con esquema de respuesta)

1. Explique la arquitectura MUA / MTA / MDA

  • Definición de cada agente y su función (usuario, transporte, entrega).
  • Encaje del MSA como punto de entrada del envío del cliente.
  • Cierre: la implementación real puede variar (agentes integrados o distribuidos).

2. Explique el papel del MSA

  • Definición: recibe el correo enviado por el cliente para su submission al sistema.
  • Por qué importa: separa submission del cliente (autenticada, puerto 587/465) del relay entre servidores (puerto 25).
  • Cierre: suele convivir con el MTA en el mismo producto.

3. Explique qué es un registro MX

  • Definición: registro DNS que indica qué servidores reciben el correo de un dominio.
  • Prioridad y posibilidad de varios servidores (respaldo).
  • Cierre: el MTA lo consulta antes de entregar; el MX no es el servidor, lo localiza.

4. Diferencie SMTP, POP3 e IMAP

  • SMTP: submission y transferencia entre servidores; puertos 25/587/465.
  • POP3: descarga desde el servidor; 110/995; sincronización limitada; puede conservar copia.
  • IMAP: acceso y gestión en el servidor; 143/993; carpetas y estados sincronizados.
  • Cierre: un cliente usa SMTP para enviar e IMAP/POP3 para recibir.

5. Explique MIME

  • Definición: estándar que permite representar contenido no limitado a texto simple.
  • Qué habilita: HTML, imágenes, adjuntos, varias partes con distintos tipos.
  • Precisión: Base64 es una codificación utilizable dentro de MIME, no MIME en sí.

6. Explique SPF, DKIM y DMARC

  • SPF: el dominio publica qué orígenes están autorizados a enviar en su nombre (política en DNS).
  • DKIM: firma criptográfica; clave privada firma, clave pública en DNS verifica; autenticidad de la firma e integridad de lo firmado.
  • DMARC: política sobre los mensajes que no superan autenticación y alineación; none/quarantine/reject; informes.
  • Cierre: son complementarios y conviene distinguir mecanismo y publicación en DNS.

7. Diferencie cliente de escritorio y webmail

  • Escritorio: aplicación instalada, cuentas configuradas con SMTP + IMAP/POP3 (o protocolos propios como MAPI).
  • Webmail: acceso por navegador vía HTTP/HTTPS, sin instalación ni configuración local.
  • Cierre: ventajas de cada uno (integración y trabajo sin conexión vs. movilidad y cero mantenimiento en el puesto).

13. Supuestos prácticos CAU

Supuesto 1 — Envía pero no recibe

Escenario: un usuario puede enviar correo sin problemas, pero no le entra nada nuevo en la bandeja de entrada.

  • a) ¿Qué indica el síntoma? Que la parte de SMTP (envío) funciona y el problema está en el acceso al buzón: POP3 o IMAP.
  • b) ¿Qué comprobar? Configuración del servidor entrante y su puerto (110/995 para POP3, 143/993 para IMAP), credenciales, y si el buzón recibe correo desde webmail (para separar cliente de servidor).
  • c) ¿Qué descarta esto? Que el fallo esté en el envío: son protocolos distintos, con configuración independiente.

Supuesto 2 — El mismo buzón en el PC y en el móvil

Escenario: una persona quiere ver los mismos mensajes, carpetas y marcas de leído en su ordenador y en su teléfono.

  • a) ¿Qué protocolo? IMAP: mantiene los mensajes en el servidor y sincroniza carpetas y estado entre dispositivos.
  • b) ¿Por qué no POP3? Porque su capacidad de sincronización es mucho más limitada: no refleja carpetas ni estados entre clientes.
  • c) ¿Qué puerto conviene? 993 (IMAP con TLS), en línea con las recomendaciones actuales de cifrado.

Supuesto 3 — Un adjunto llega ilegible

Escenario: un usuario recibe un mensaje cuyo archivo adjunto aparece como texto extraño o no se abre.

  • a) ¿Dónde mirar? En el tratamiento del contenido del mensaje: MIME y su codificación (por ejemplo, Base64), el cliente utilizado y el formato del adjunto.
  • b) ¿Es un problema de SMTP? No necesariamente: SMTP ha transportado el mensaje; lo que falla es la representación o interpretación del contenido.
  • c) ¿Prueba útil? Abrir el mismo mensaje desde webmail u otro cliente para determinar si el problema está en el mensaje o en el cliente concreto.

Supuesto 4 — Correo aparentemente enviado desde un dominio no autorizado

Escenario: llegan mensajes que dicen proceder de un dominio de la organización, pero salen de servidores desconocidos.

  • a) ¿Qué mecanismos entran en juego? SPF (qué orígenes están autorizados a enviar con ese dominio), DKIM (firma e integridad) y DMARC (política y alineación, con informes).
  • b) ¿Basta con SPF? No: SPF no verifica directamente el From visible; por eso DMARC añade la alineación y decide el tratamiento.
  • c) ¿Qué política puede aplicarse? none, quarantine o reject, según la decisión del propietario del dominio.

Supuesto 5 — «Me llega spam enviado desde mi propia dirección»

Escenario: una usuaria recibe mensajes que aparentan estar enviados por ella misma.

  • a) ¿Qué está ocurriendo? Una suplantación (spoofing) del remitente mostrado: SMTP no verifica por sí mismo la identidad del emisor (la amenaza se estudia en el Tema 25).
  • b) ¿Significa que su cuenta está comprometida? No necesariamente: falsificar el From no requiere acceso al buzón. Conviene comprobar indicios adicionales antes de concluirlo.
  • c) ¿Qué reduce el problema a nivel de dominio? Configurar correctamente SPF, DKIM y DMARC, que permiten a los receptores detectar y tratar esos mensajes.

Supuesto 6 — Un mensaje no llega al destinatario

Escenario: un envío a otra administración no aparece en el buzón del destinatario y no hay error visible para el usuario.

  • a) ¿Qué revisar primero? El registro MX del dominio de destino (a qué servidores debía entregarse) y el recorrido por los MTA.
  • b) ¿Qué evidencia hay en el propio mensaje? Las cabeceras Received, que permiten localizar dónde se interrumpió el recorrido.
  • c) ¿Qué otras causas encajan? Que el receptor lo haya tratado conforme a su política (por ejemplo, cuarentena por DMARC) o filtros del destinatario.

Supuesto 7 — Configurar el correo en un puesto nuevo

Escenario: hay que configurar la cuenta corporativa en el cliente de escritorio de un equipo recién entregado.

  • a) ¿Qué datos son imprescindibles? Servidor y puerto de envío (SMTP) — habitualmente 587 con STARTTLS/TLS o 465 con TLS implícito — y servidor y puerto de recepción: IMAP 993 o POP3 995.
  • b) ¿Qué elegir para recepción? IMAP si la persona usa varios dispositivos y quiere el buzón sincronizado.
  • c) ¿Y si el producto usa protocolos propios? Puede configurarse mediante MAPI u otros mecanismos del fabricante — que no son equivalentes a SMTP/IMAP.

14. Matriz de memorización

Concepto Lo que debo recordar
MUA Programa/interfaz que usa la persona para redactar, enviar y leer correo
MSA Recibe el correo enviado por el cliente (submission); explica el puerto 587
MTA Transporta y encamina mensajes entre servidores mediante SMTP
MDA Entrega el mensaje en el buzón del destinatario
MX Registro DNS que indica qué servidores reciben el correo del dominio; con prioridad
From Remitente mostrado del mensaje
To Destinatario principal
Cc Copia visible para los demás destinatarios
Cco/Bcc Copia oculta: no visible para los demás destinatarios
Received Traza añadida por los servidores; permite reconstruir el recorrido
MIME Estándar para contenido no limitado a texto simple (HTML, imágenes, adjuntos); Base64 es una codificación dentro de él
SMTP Submission + transferencia entre servidores; 25 relay, 587 submission, 465 submission con TLS implícito
POP3 Descarga/recuperación desde el servidor; 110 y 995; puede conservar copia; sincronización limitada
IMAP Acceso y gestión en el servidor; 143 y 993; carpetas y estados sincronizados
SPF Autoriza orígenes de envío del dominio; política publicada en DNS
DKIM Firma + integridad; privada firma, pública en DNS verifica; la firma viaja en el mensaje
DMARC Política + alineación + informes; none/quarantine/reject; se publica en DNS bajo _dmarc
Webmail Acceso por navegador (HTTP/HTTPS), sin instalación ni configuración local
Outlook / Thunderbird Clientes de escritorio: SMTP para enviar e IMAP/POP3 para recibir (o protocolos propios como MAPI)

15. Resumen final: si mañana fuera el examen

  • Arquitectura: MUA (lo usa la persona) → MSA (recibe el envío del cliente) → MTA (transporta entre servidores) → MDA (entrega en el buzón). La implementación real puede variar.
  • MX = registro DNS que indica qué servidores reciben el correo del dominio, con prioridad. No es el servidor: lo localiza.
  • Recorrido: MUA → MSA/submission → MTA → consulta MX → MTA destino → MDA → buzón → POP3/IMAP → MUA destinatario.
  • Mensaje: cabeceras (From, To, Cc visibles, Cco ocultos, Subject, Date, Message-ID, Received) y cuerpo. Received reconstruye el recorrido. MIME permite contenido no textual; Base64 es una codificación usada dentro de MIME.
  • SMTP = submission + transferencia: 25 relay · 587 submission (STARTTLS/TLS) · 465 submission con TLS implícito — 587 y 465 no son lo mismo. SMTP no sirve para consultar el buzón.
  • POP3 (110/995): descarga; puede conservar copia en el servidor; sincronización limitada. IMAP (143/993): mensajes en el servidor, con carpetas y estados sincronizados entre dispositivos.
  • SPF → autoriza orígenes · DKIM → firma + integridad · DMARC → política + alineación + informes (none/quarantine/reject). En DNS: la política SPF, la clave pública DKIM (la firma va en el mensaje) y la política DMARC bajo _dmarc.
  • Clientes: escritorio, webmail y móvil. Un cliente usa SMTP para enviar e IMAP/POP3 para recibir; MAPI (entorno Exchange) es un mecanismo distinto, no otro nombre de los estándares.
  • Las recomendaciones actuales favorecen TLS tanto en submission como en el acceso al buzón.
