1. Concepto de virtualización: host, guest y VM

La virtualización es la tecnología que permite abstraer recursos físicos y presentarlos como recursos virtuales independientes y gestionables. Aplicada a equipos y servidores, permite ejecutar varias máquinas virtuales sobre un mismo host físico, cada una funcionando de forma aislada de las demás.

  • Host (anfitrión): el equipo físico que proporciona los recursos reales (CPU, memoria, disco, red).
  • Guest (invitado): el sistema o software invitado que se ejecuta dentro de una máquina virtual. En el nivel básico: una VM normalmente ejecuta su propio sistema operativo invitado.
  • Máquina virtual (VM): la máquina definida por software, con recursos virtuales propios — CPU virtual, memoria, almacenamiento y red virtuales — sobre la que se ejecuta el invitado.
💡 Analogía
El host es un edificio; las VM, apartamentos independientes: cada inquilino (el sistema invitado) tiene sus habitaciones y su puerta con llave, y no ve los demás apartamentos, aunque todos compartan la estructura y los suministros del edificio (el hardware físico).

2. El hipervisor: concepto y tipos

El hipervisor (o VMM, Virtual Machine Monitor) es la capa de software que crea y gestiona las máquinas virtuales, asigna los recursos y mantiene su aislamiento.

Tipo 1 (bare-metal)

  • Se ejecuta directamente sobre el hardware, sin un sistema operativo convencional debajo.
  • Es el modelo habitual en servidores y producción.
  • Ejemplos principales: VMware ESXi, Microsoft Hyper-V, Xen.

Tipo 2 (hosted, alojado)

  • Se ejecuta sobre un sistema operativo anfitrión convencional, como una aplicación más.
  • Habitual en escritorio, pruebas y desarrollo.
  • Ejemplos: VMware Workstation/Fusion, VirtualBox, Parallels Desktop.
🧠 Para memorizar — la diferencia fundamental
TIPO 1: hardware → hipervisor → VM.
TIPO 2: hardware → SO anfitrión → hipervisor → VM.
⚠️ No confundir — trampa de examen: Hyper-V
Aunque se habilite desde Windows (como rol o característica), Hyper-V es un hipervisor de tipo 1: al activarlo, el hipervisor se coloca directamente sobre el hardware y el propio Windows pasa a ejecutarse por encima como partición raíz. Que se instale «desde» un SO no lo convierte en tipo 2.
📌 Precisión — KVM y Proxmox VE
KVM → tecnología/módulo de virtualización integrado en el kernel Linux, que convierte al núcleo en capaz de ejecutar máquinas virtuales.
Proxmox VE → plataforma de virtualización y gestión que integra KVM para máquinas virtuales y LXC para contenedores.
Son ejemplos del ecosistema de virtualización de código abierto; no deben clasificarse sin más como «productos tipo 1 equivalentes a ESXi».

3. Tipos de virtualización

Virtualización completa (full virtualization)

  • El hipervisor presenta a la VM un hardware virtual completo.
  • El SO invitado se ejecuta sin modificaciones significativas, sin ser consciente de la virtualización, con aislamiento completo.
  • Se apoya habitualmente en las extensiones hardware de virtualización del procesador — Intel VT-x y AMD-V — que aceleran la ejecución (no todas las implementaciones dependen obligatoriamente de ellas).

Paravirtualización

  • El software invitado utiliza interfaces específicas de virtualización para comunicarse con el hipervisor, reduciendo el coste de determinadas operaciones.
  • No implica necesariamente modificar todo el sistema operativo: puede afectar a componentes concretos.
  • Distinción conceptual: la paravirtualización (el enfoque general) no es lo mismo que los drivers paravirtualizados — controladores optimizados para el entorno virtual que puede usar incluso un SO con virtualización completa (VirtIO es un ejemplo puntual).

Ampliación: contenedores

  • VM → hardware virtual + SO propio por máquina.
  • Contenedor → procesos aislados que comparten el kernel del host; empaqueta una aplicación con sus dependencias, no un SO completo.
  • Los contenedores suelen ser más ligeros que una VM (arranque y consumo menores).
Criterio Máquina virtual Contenedor
Qué se virtualiza/aísla El hardware completo Procesos sobre un kernel compartido
Sistema operativo Propio en cada VM Comparte el del host
Peso y arranque Mayor Mucho más ligero
Aislamiento Muy alto Menor que una VM

4. Casos de uso

  • Consolidación de servidores: sustituir varios servidores físicos infrautilizados por un host que ejecuta varias VM, aprovechando mejor la capacidad.
  • Pruebas y desarrollo: crear y destruir VM bajo demanda para probar software o cambios sin arriesgar producción.
  • Alta disponibilidad (HA): configuraciones con varios hosts que permiten reubicar las VM ante fallos o mantenimientos.
  • Migración en caliente: traslado de una VM en ejecución entre hosts con interrupción mínima o prácticamente imperceptible, según la tecnología y configuración (ejemplos: vMotion, Live Migration). No debe afirmarse «cero interrupción» garantizada en cualquier situación.
  • Recuperación ante desastres (DR): replicar VM completas hacia otro emplazamiento para recuperar el servicio con rapidez.
  • VDI (escritorios virtuales): alojar los escritorios de los usuarios como VM centralizadas a las que se accede de forma remota, con gestión y actualización centralizadas.
  • Relación con la nube: la virtualización constituye una de las tecnologías fundamentales utilizadas por los proveedores cloud (el detalle, en el Tema 32).

Snapshot

📌 Imprescindible para el examen — SNAPSHOT ≠ BACKUP
Snapshot: captura de un estado de la VM que permite volver rápidamente a un punto anterior — muy útil antes de un cambio arriesgado.
Un snapshot no sustituye a una estrategia de copia de seguridad: reside junto a la propia VM y su infraestructura, y no está pensado para retención ni recuperación ante la pérdida del host o del almacenamiento. El backup es una copia independiente destinada a la recuperación.

5. Ventajas y desventajas

Ventajas

  • Consolidación y mejor aprovechamiento del hardware.
  • Ahorro de infraestructura (menos servidores físicos que alojar, alimentar y refrigerar) — con matiz: virtualizar no siempre reduce costes; depende de la escala, las licencias, el almacenamiento, la red, la administración y la HA necesarias.
  • Aislamiento entre máquinas virtuales.
  • Rapidez de despliegue y flexibilidad: crear, clonar o eliminar una VM lleva minutos.
  • Snapshots para volver atrás ante cambios arriesgados.
  • Migración en caliente para mantenimiento con interrupción mínima.

Desventajas

  • Overhead: la capa de virtualización consume recursos y puede introducir cierta pérdida de rendimiento (reducida por las extensiones hardware).
  • Punto único de fallo: si el host falla y no existe alta disponibilidad, todas sus VM caen a la vez.
  • Mayor complejidad de gestión y planificación de recursos.
  • Overcommit: asignar recursos virtuales que pueden superar la capacidad física, suponiendo que no todas las VM usarán el máximo simultáneamente; mal controlado, degrada el rendimiento de todo el host.
  • Posibles costes de licenciamiento del software de virtualización empresarial.
🧠 Para memorizar — el punto único de fallo
Sin alta disponibilidad: HOST → varias VM → fallo del host → varios servicios afectados a la vez. Es la desventaja estructural clásica, y un caso práctico habitual.

Existen soluciones comerciales y de código abierto de virtualización; para este tema interesan principalmente los conceptos y arquitecturas, no la evolución comercial de los fabricantes.

6. Datos y anclas de memoria

  • HOST → físico · GUEST → invitado · VM → ordenador virtual (definida por software).
  • Hipervisor/VMM = crea, gestiona, asigna y aísla.
  • TIPO 1 → sobre el hardware · TIPO 2 → sobre el SO anfitrión. Hyper-V = tipo 1 (aunque se active desde Windows).
  • KVM = módulo del kernel Linux · Proxmox VE = plataforma (KVM + LXC).
  • Full virtualization: hardware virtual + SO sin modificar (+ VT-x/AMD-V). Paravirtualización: interfaces específicas para reducir costes de operación.
  • VM → SO propio · CONTENEDOR → kernel compartido (más ligero).
  • Casos de uso: consolidación · pruebas · HA · migración en caliente · DR · VDI · base de la nube.
  • SNAPSHOT → volver atrás rápidamente · BACKUP → copia para recuperación (no son lo mismo).
  • MIGRACIÓN EN CALIENTE → mover VM funcionando (interrupción mínima según tecnología, no «cero garantizado»).
  • Overcommit = prometer más recursos virtuales que los físicos; overhead = coste de la capa de virtualización.
  • Sin HA: host único = punto único de fallo.

8. Posibles trampas de examen

  • «Hyper-V es tipo 2 porque se instala desde Windows» — falso: es tipo 1; Windows queda como partición raíz sobre el hipervisor.
  • «KVM es un producto equivalente a ESXi» — impreciso: KVM es una tecnología/módulo del kernel Linux, no un producto empaquetado.
  • «Proxmox VE es simplemente un hipervisor» — impreciso: es una plataforma de virtualización y gestión que integra KVM (VM) y LXC (contenedores).
  • «VM y contenedor son lo mismo» — falso: la VM tiene SO propio sobre hardware virtual; el contenedor comparte el kernel del host.
  • «Un snapshot es una copia de seguridad» — falso: permite volver atrás rápidamente, pero no sustituye al backup.
  • «Virtualización y cloud son sinónimos» — falso: la nube usa virtualización, pero es un modelo de servicio (Tema 32).
  • «Los contenedores llevan su propio sistema operativo completo» — falso: comparten el kernel del host.
  • «Virtualizar elimina los puntos únicos de fallo» — al revés sin HA: un host único concentra el riesgo de varias VM.
  • «La migración en caliente garantiza cero interrupción en cualquier situación» — matiz: la interrupción es mínima o prácticamente imperceptible según tecnología y configuración.
  • «Virtualizar siempre reduce costes» — matiz: depende de escala, licencias, almacenamiento, red, administración y HA.
  • «La virtualización completa exige modificar el SO invitado» — invertido: es la paravirtualización la que usa interfaces específicas; la completa ejecuta el SO sin modificaciones significativas.

10. Posibles preguntas cortas (con esquema de respuesta)

1. Defina la virtualización y sus conceptos básicos

  • Definición: abstraer recursos físicos y presentarlos como virtuales, independientes y gestionables.
  • En equipos/servidores: varias VM sobre un host físico.
  • Host (físico) · guest (invitado) · VM (máquina definida por software con recursos virtuales).

2. Diferencie los hipervisores de tipo 1 y tipo 2

  • Definición de hipervisor/VMM.
  • Tipo 1: sobre el hardware (ESXi, Hyper-V, Xen); tipo 2: sobre un SO anfitrión (VirtualBox, Workstation).
  • Los dos esquemas de capas; el caso Hyper-V como matiz.

3. Explique la virtualización completa y la paravirtualización

  • Completa: hardware virtual, SO sin modificaciones significativas, aislamiento; apoyo de VT-x/AMD-V.
  • Paravirtualización: interfaces específicas que reducen el coste de operaciones; distinción con los drivers paravirtualizados.

4. Compare máquina virtual y contenedor

  • VM: hardware virtual + SO propio; aislamiento muy alto; más pesada.
  • Contenedor: procesos aislados sobre kernel compartido; más ligero; menor aislamiento.
  • Cierre: el tema se centra en las VM; el contenedor se cita para diferenciar.

5. Explique los principales casos de uso de la virtualización

  • Consolidación, pruebas/desarrollo, HA, migración en caliente, DR, VDI.
  • Relación con la nube en una frase (tecnología fundamental; Tema 32).

6. Explique las ventajas y desventajas de la virtualización

  • Ventajas: aprovechamiento, ahorro de infraestructura (con matiz), aislamiento, rapidez, snapshots, migración.
  • Desventajas: overhead, punto único de fallo sin HA, complejidad, overcommit, licencias.

7. Explique qué es un snapshot y su diferencia con un backup

  • Snapshot: captura de estado para volver atrás rápidamente; uso típico antes de cambios.
  • Backup: copia independiente para recuperación; el snapshot no lo sustituye (reside junto a la propia infraestructura).

11. Supuestos prácticos

Supuesto 1 — Servidores infrautilizados

Escenario: un ayuntamiento tiene cinco servidores físicos antiguos, cada uno con un servicio y un uso medio de CPU muy bajo.

  • a) ¿Qué solución encaja? Consolidación mediante virtualización: un host (o mejor, varios con HA) ejecutando cinco VM, una por servicio.
  • b) ¿Qué se gana? Aprovechamiento del hardware, ahorro de infraestructura, rapidez de despliegue y gestión centralizada.
  • c) ¿Qué riesgo hay que valorar? El host como punto único de fallo si no se configura alta disponibilidad, y el dimensionamiento (evitar overcommit excesivo).

Supuesto 2 — Probar una actualización sin miedo

Escenario: hay que probar una actualización mayor de una aplicación de gestión sin afectar a producción.

  • a) ¿Cómo ayuda la virtualización? Clonando una VM de pruebas idéntica a producción y ensayando allí la actualización.
  • b) ¿Y en producción, llegado el momento? Tomar un snapshot antes de aplicar el cambio: si algo falla, se vuelve rápidamente al estado anterior.
  • c) ¿Sustituye ese snapshot al backup de la VM? No: el snapshot es un punto de retorno rápido, no una copia de seguridad independiente.

Supuesto 3 — Mantenimiento sin cortar el servicio

Escenario: hay que sustituir la fuente de alimentación de un host que ejecuta VM en producción.

  • a) ¿Qué mecanismo lo permite? La migración en caliente: trasladar las VM en ejecución a otro host antes del mantenimiento, si la infraestructura lo permite (almacenamiento compartido, hosts compatibles).
  • b) ¿Con qué expectativa de corte? Interrupción mínima o prácticamente imperceptible según la tecnología y configuración — no «cero garantizado» en cualquier situación.
  • c) Ejemplos de tecnologías. vMotion (VMware), Live Migration (Hyper-V) — como ejemplos, no contenido de marca.

Supuesto 4 — El host que se cayó con todo dentro

Escenario: un único host sin HA alberga diez VM con servicios municipales; una avería de hardware lo detiene por completo.

  • a) ¿Qué ha ocurrido conceptualmente? Se ha materializado el punto único de fallo: HOST → varias VM → fallo del host → varios servicios afectados a la vez.
  • b) ¿Cómo se mitiga? Alta disponibilidad: varios hosts, almacenamiento compartido y mecanismos de reubicación de VM; además, copias de seguridad independientes.
  • c) ¿Qué lección deja sobre la consolidación? Concentrar servicios exige plan de contingencia: la consolidación sin HA aumenta el impacto de cada fallo físico.

Supuesto 5 — «Con los snapshots ya tenemos copia»

Escenario: se propone eliminar las copias de seguridad de varias VM «porque ya se hacen snapshots semanales».

  • a) ¿Cuál es el error? Confundir snapshot con backup: el snapshot reside en la propia infraestructura; si se pierde el host o el almacenamiento, se pierden la VM y sus snapshots juntos.
  • b) ¿Para qué sí sirven los snapshots? Retorno rápido a un estado anterior ante cambios fallidos — complemento, no sustituto.
  • c) ¿Qué debe mantenerse? Una estrategia de copia de seguridad independiente (su detalle corresponde al Tema 23).

13. Resumen final: si mañana fuera el examen

  • Virtualización = abstraer recursos físicos en virtuales; en servidores: varias VM sobre un host. Host = físico · guest = invitado · VM = máquina por software.
  • Hipervisor (VMM): crea, gestiona, asigna, aísla. Tipo 1: hardware → hipervisor → VM (ESXi, Hyper-V, Xen). Tipo 2: hardware → SO anfitrión → hipervisor → VM (VirtualBox, Workstation, Parallels). Hyper-V es tipo 1 aunque se active desde Windows (partición raíz).
  • KVM = módulo del kernel Linux · Proxmox VE = plataforma que integra KVM (VM) y LXC (contenedores).
  • Completa (SO sin modificar, VT-x/AMD-V) vs. paravirtualización (interfaces específicas); drivers paravirtualizados como concepto aparte. VM (SO propio) ≠ contenedor (kernel compartido, más ligero).
  • Casos de uso: consolidación · pruebas · HA · migración en caliente (interrupción mínima según tecnología) · DR · VDI · base tecnológica del cloud (T32).
  • Snapshot ≠ backup: volver atrás rápido vs. copia independiente para recuperación.
  • Ventajas: aprovechamiento, ahorro de infraestructura (según escala y licencias), aislamiento, rapidez, snapshots, migración. Desventajas: overhead, punto único de fallo sin HA (HOST → VMs → fallo → varios servicios caídos), complejidad, overcommit, licencias.
  • Productos solo como ejemplos: interesan los conceptos y arquitecturas, no la evolución comercial de los fabricantes.
